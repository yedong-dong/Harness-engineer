# PRD 业务+技术深层分析

## 使用方式

1. 用户提供 PRD 文字 + 技术方案（强烈建议同时提供，有技术方案时分析更准确）
2. Agent 逐模块分析 → 技术方案明确的直接引用，没提的合理推断 → **暂停，用户确认推断**
3. 确认后挖掘逻辑漏洞 → 输出分析报告

### 三阶段流程

```
PRD + 技术文档
     │
     ▼
┌─ 阶段1：业务理解 + 技术反推 ───────────────────────────────┐
│                                                          │
│  逐模块分析（读取 references/analysis-method.md）：         │
│    ① 业务层：功能价值、涉及实体、影响指标                    │
│    ② 技术层：                                              │
│       ├─ 有技术方案？                                      │
│       │   YES → 提取技术方案中的实现细节（接口/数据结构/状态机）│
│       │        → 标注「技术方案明确」                        │
│       │        → 技术方案没覆盖的部分 → 合理推断 + 标记「待确认」│
│       │   NO  → 基于 PRD + 行业通用做法推断                  │
│       │        → 全部标记「待确认」                          │
│    ③ 关键逻辑用伪代码表达                                   │
│                                                          │
│  ★ 暂停 → 用户确认技术推断是否正确                          │
│      → 补充技术方案或纠正推断方向                            │
└──────────────────────────────────────────────────────────┘
     │
     ▼
┌─ 阶段2：逻辑漏洞挖掘 ─────────────────────────────────────┐
│                                                          │
│  对每个确认的技术实现点：                                   │
│    · 正常路径的隐藏风险（如原子性、数据一致性）               │
│    · 异常/边界下的逻辑漏洞（如并发、超时、中断多天）          │
│    · 产品没考虑到的场景？开发容易漏掉的判断？                 │
│    · 竞品可能的差异点（如果 PRD 有竞品相关描述）              │
│                                                          │
│  每个漏洞附带：场景推演 + 为什么易被遗漏 + 验证方向           │
└──────────────────────────────────────────────────────────┘
     │
     ▼
┌─ 阶段3：输出分析报告 ─────────────────────────────────────┐
│                                                          │
│  输出到 PRD/<项目>/output/<需求名>-深层分析.md              │
│  若 PRD 下无对应目录，则输出到 docs/notes/business-analysis/  │
│                                                          │
│  报告结构：                                                │
│    1. 业务全景（动机、实体关系、影响指标）                    │
│    2. 逐模块技术推断（含伪代码和数据结构推断）                │
│    3. 逻辑漏洞挖掘（场景推演 + 为什么易被遗漏）              │
│    4. 测试要点（含关键验证伪代码）                           │
│    5. 待确认清单（待跟产品/开发确认的问题 + 默认假设 + 风险等级）│
└──────────────────────────────────────────────────────────┘
```

## 核心原则

1. **推断而非猜测**：技术推断必须有依据（PRD 描述 / 技术文档 / 行业通用做法），不确定时标记"待确认"
2. **深挖而非铺开**：每个模块挖 2-3 个深层漏洞 > 每个模块浅覆盖所有功能点
3. **业务后果优先**：每个漏洞描述必须关联业务后果（"这会导致XX"），不只说技术现象（"状态不一致"）
4. **用伪代码表达**：关键逻辑用伪代码/流程图描述，比纯文字更精确
5. **报告可独立阅读**：不需要看原 PRD 就能理解分析的完整逻辑
6. **技术方案优先**：提供了技术方案时，实现细节以技术方案为准——方案明确的直接引用，没提的再合理推断。避免纯推断被产品/开发以"你猜错了"驳回

## 与 prd-testcase-xmind 的关系

两个 Skill 互补，互不替代：

| | prd-testcase-xmind | prd-business-analysis |
|---|---|---|
| 输入 | PRD + 技术文档 | PRD + 技术文档 |
| 输出 | 测试用例 .xmind | 分析报告 .md |
| 目标 | 生成可执行用例 | 挖掘逻辑漏洞 |
| 方法 | 四维要素 → 并行生成 → 评估 | 业务→技术推断→漏洞推演 |
| 人工节点 | 澄清确认（暂停1次） | 技术推断确认（暂停1次） |

建议流程：先跑 prd-business-analysis 挖出漏洞 → 再跑 prd-testcase-xmind 生成用例（漏洞点自动转化为高优先级用例）

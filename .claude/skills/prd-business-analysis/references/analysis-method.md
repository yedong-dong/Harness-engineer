# 业务+技术深层分析方法论

## 金字塔：从 PRD 文字到逻辑漏洞

```
PRD 文字（What）
     │
     ▼
① 业务层理解（Why + Who）
  · 这个需求为什么现在做？
  · 涉及哪些实体？关系是什么？
  · 影响什么业务指标？
     │
     ▼
② 技术层反推（How）
  · 后端大概率怎么实现？
  · 用什么数据结构？什么算法？
  · 状态机怎么流转？
     │
     ▼
③ 逻辑漏洞挖掘（What Could Go Wrong）
  · 基于实现方式，什么场景下会出问题？
  · 产品和开发都容易遗漏的盲区？
     │
     ▼
④ 测试要点（How to Verify）
  · 针对漏洞的验证方案（含伪代码）
```

---

## ① 业务层理解

### 核心问题

拿到一个 PRD 功能，先问三个问题：

| 问题 | 找什么 | 例子（女性权益聚合） |
|------|--------|---------------------|
| 为什么现在做？ | 业务时机 | 女性留存可能下滑/竞品有类似功能 |
| 谁受益谁受损？ | 利益方 | 认证女性受益（权益感知），男性"受损"（被限制匹配次数） |
| 影响什么指标？ | 业务指标 | 认证率、7日留存、女性投诉率 |

### 实体关系梳理

```
用一句话描述核心实体和关系：
"用户（性别+认证状态）→ 决定权益层级 → 权益包含包装功能+新增功能 → 签到是认证后的独立子系统"

然后画实体关系图（ASCII 即可）。
```

## ② 技术层反推

### 核心方法

不是瞎猜，是有依据的推断：

```
推断依据优先级:
  1. 技术文档明确写了 → 直接引用
  2. PRD 暗示了 → 推断 + 标记"待确认"
  3. 行业通用做法 → 推断 + 标注依据
  4. 完全没有线索 → 列出可能的实现方案，逐一分析漏洞
```

### 推断框架

对每个模块，回答：

```
数据结构: 用什么存？（表结构 / Redis Key / 缓存 Key）
算法逻辑: 怎么算？（排序 / 分片 / 状态流转）
接口设计: 怎么调？（入参 / 出参 / 状态码）
异常处理: 什么情况下会失败？（并发 / 超时 / 数据不存在）
```

### 伪代码的价值

文字描述逻辑容易模糊，伪代码能暴露真正的问题。比如：

```
// 文字描述: "签到成功后发奖励并更新状态"
// 伪代码暴露的问题:
grantReward(userID, packID)  // ← 步骤1: 发奖
updateStatus(userID, day, 2)  // ← 步骤2: 写状态
// 问题: 如果步骤2失败，用户拿到了奖励但状态没更新 → 可重复签到
```

### 案例：从 PRD 反推技术实现

**参考案例 1**（来自用户 reference — All Banner 优化）：

```
PRD 描述: "将 Banner&AD&Activity Banner 合并为 All Banner，统一管理"

反推数据库设计:
  ┌────────────┬──────┬──────┬──────┬──────┐
  │ type       │ prio │ btype│ ident│ extra│ ...
  ├────────────┼──────┼──────┼──────┼──────┤
  │ 普通Banner  │  ✓   │  ✓   │      │      │
  │ Ad         │  ✓   │  ✓   │      │  ✓   │
  │ Activity   │  ✓   │  ✓   │  ✓   │      │
  └────────────┴──────┴──────┴──────┴──────┘

关键发现: 合并后不同 type 的必填字段不同，创建时必须保证入表字段对应正确。
测试核心: 各种 type 组合创建 → 确认落表字段无串位。
```

**参考案例 2**（来自用户 reference — 语音匹配优先级）：

```
PRD 描述: "付费发起的和iOS GCC新用户自动发起的匹配优先级最高"

反推技术方案:
  方案A: Redis Sorted Set
    · 入队时根据优先级计算 Score
    · 消费线程 ZRevRange 按 Score 降序处理
    · 问题: 高优持续涌入 → 低优饥饿

  方案B: RabbitMQ 优先级队列
    · 声明 x-max-priority
    · 入队设置 priority 值
    · 问题: 同样会出现低优饥饿 + 死信队列堆积

从技术方案反推出的测试场景:
  1. 3 队列拆分（普通+共享+高优）→ 分配独立线程资源
  2. ZSet 数据量大 → 自动分片
  3. 高优持续入队 → 普通消息无积压
```

**参考案例 3**（来自女性权益聚合分析 — 签到）：

```
PRD 描述: "连续登录7日领取签到奖励，中断当天奖励不可领取"

反推接口逻辑:
  func Checkin(userID):
    1. 校验认证状态
    2. 查今天是否可签到 (status=1)
    3. 查是否已签到 (status=2) → 幂等返回
    4. 发奖励 → 更新状态

暴露的关键问题:
  · 步骤4中"发奖励"和"更新状态"的原子性
  · 先发奖还是先写状态？中途失败如何恢复？
```

## ③ 逻辑漏洞挖掘

### 漏洞分类法

```
技术漏洞（开发容易漏）:
  · 并发/分布式场景下的原子性问题
  · 缓存一致性（写了DB没清缓存）
  · 异步任务的失败重试和补偿
  · 状态机里的不可达状态和死循环

业务漏洞（产品容易漏）:
  · "词不达意"：PRD 描述和实际能力不匹配
  · 极端用户路径：用户不按产品设想的"正常路径"走
  · 利益冲突：功能对一类用户有利但对另一类有损
  · 时间维度：定义里使用模糊词（"下次"、"连续"、"近期"）

竞品漏洞（产品+开发都容易漏）:
  · 竞品已有的能力我们没有 → 客诉
  · 竞品踩过的坑 → 我们重蹈覆辙
```

### 漏洞挖掘技巧

**技巧 1：追问"如果失败会怎样"**

```
正常路径: 签到 → 发奖 → 完成
追问: 发奖成功但状态更新失败 → 用户看到什么？能再次签到吗？
追问: 发奖失败但状态已更新 → 用户签到了但没拿到奖励 → 投诉
```

**技巧 2：追问"如果用户不按套路出牌"**

```
产品设想的路径: 每天打开App→签到→领奖
用户可能的路径:
  · 签到后卸载重装 → 签到状态还在吗？
  · 第1天签到→第2-6天不登→第7天登录 → 能签吗？
  · 改手机系统时间 → 能提前签未来天的奖励吗？
```

**技巧 3：追问"定义里的模糊词"**

```
PRD 里的模糊词清单:
  · "连续" → 断了一天算不算连续？
  · "下次" → 具体什么条件？
  · "实时" → 有缓存吗？延迟多大算实时？
  · "每日" → 00:00重置还是24小时间隔？
  · "仅一次" → 什么维度的一次？用户维度还是设备维度？
```

### 每个漏洞的标准描述格式

```
### 漏洞 N：<一句话描述>

**场景推演**: <具体步骤，从用户视角出发>
**为何易被遗漏**: <产品/开发/测试各自可能没想到什么>
**风险等级**: 高/中/低 — <对业务指标的影响>
**验证方向**: <最小可验证步骤>
```

## ④ 测试要点

### 不是罗列用例，是给出验证方向

- 针对每个漏洞给出 1-3 个最小验证步骤
- 关键验证用伪代码（Go/Python 均可）
- 区分"可自动化"和"需手动判断"

### 伪代码示例

```go
// 签到并发幂等
func TestCheckinIdempotent() {
    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            resp := post("/female/checkin")
            fmt.Println(resp)
        }()
    }
    wg.Wait()
    // 断言: 只发了一次奖励
    rewards := getRewardRecord(userID)
    assert(len(rewards) == 1)
}
```

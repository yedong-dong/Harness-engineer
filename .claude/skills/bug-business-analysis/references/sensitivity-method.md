# 业务敏感性分析方法论

## 什么是业务敏感性

业务敏感性 = 看到 Bug 时，能透过技术现象看到业务本质。

```
普通测试："充值金额为0时报错了，提 Bug"
业务敏感的测试：
  "充值金额为0时报错了。但进一步看——
   ① PRD 说金额范围 1-100000，0 不在范围内，说明后端参数校验按了 PRD，但前端没拦截
   ② 前端为什么没拦截？PRD 第3章说了"客户端输入校验"，但没给出具体校验规则清单
   ③ 同类问题：金额上限 100000，前端是否也没拦截？
   ④ 业务影响：如果用户输入 0 → 调用支付接口 → 支付渠道报错 → 用户困惑 → 投诉
   ⑤ 用例补全：金额输入的客户端校验用例需要补充覆盖 0/负数/小数/超长整数
   ⑥ 规则沉淀：PRD 中涉及输入范围的，必须明确前端校验规则和后端校验规则的边界"
```

## 四维分析方法

### ① 根因反推

不是复述 Bug 现象，而是推断「什么假设错了」。

```
Bug 现象 → 推断根因的技术层：                  推断根因的业务层：
─────────────────────────────          ────────────────────────
"签到发奖后刷新，又可以签一次"            "PRD 说签到满7天领奖，没提断签后怎么算
                                     → 产品默认用户每天都签到，没考虑中断"

推断：
· status=1 → 发奖 → status=2              推断：
  但发奖和写状态不是原子的                "连续"和"累计"的区别没定义
· 发奖成功、写状态超时 → 事务回滚了发奖吗？
· 前端拿到发奖成功就更新UI，不等状态写入
```

**判断依据来源**：

| 来源 | 可信度 | 处理方式 |
|------|--------|---------|
| 能看到服务端日志/代码 | 高 | 直接引用 |
| 能从现象精确推断（如并发=原子性） | 中 | 推断 + 标注"待日志验证" |
| PRD + 行业通用做法 | 中 | 推断 + 标注"待确认" |
| 仅凭现象猜测 | 低 | 列出多个可能根因 |

### ② 测试盲区分析

每个 Bug 回答三个问题：

```
Q1: 用例设计时假设了什么？
  例："假设用户不会在签到途中断网" → 这是不合理的假设
  例："假设前端已经做了校验" → 用例只测了后端校验

Q2: 这个假设为什么是错的？
  例：PRD 没有明确前端校验清单，但测试应该主动问
  例：技术方案说了"客户端不信任服务端返回"，但服务端是否需要信任客户端传入？

Q3: 有多少同类盲区？
  例：不仅签到，所有涉及"发奖+写状态"的功能都有原子性问题
  例：不仅充值金额，所有数据输入的客户端校验都需要独立覆盖
```

**盲区分类**：

```
A类盲区 — 维度缺失：整个测试维度被漏掉（如并发、数据一致性、缓存延迟）
B类盲区 — 边界缺失：某个功能的边界值/异常值没覆盖
C类盲区 — 精度缺失：用例有了但步骤/预期不够精确，无法发现 Bug
D类盲区 — 假设错误：测试基于了错误的假设（如"前端做了校验""API 不会超时"）
```

### ③ 业务影响评估

```
不是"导致状态不一致"（技术语言）
而是"用户签到成功后刷新页面，显示未签到，用户以为没签到又签了一次，
     第二天发现奖励少了一天 → 投诉"（用户语言 + 业务后果）

影响评估公式：
  影响范围 × 触发概率 × 用户感知强度 = 风险等级

  高：全量用户 × 必然触发 × 直接影响核心体验（支付/签到/等级）
  中：特定条件 × 低概率 × 影响体验但不阻断
  低：极端条件 × 极低概率 × 仅显示问题
```

### ④ 关联风险扫描

```
以 Bug 为圆心，向外扫描：

1. 相同数据结构：
   "签到用了 user_status 表标记状态，积分也用了同一张表 → 积分是否存在同类原子性问题？"

2. 相同实现模式：
   "充值用了 Redis + DB 双写，提现也用了 → 提现的缓存一致性？"

3. 相同产品逻辑：
   "签到要求'连续7天不断'，等级计算要求'连续30天活跃' → 等级是否也有中断定义模糊？"

4. 相同开发：
   "这个模块是 X 写的，他负责的另一个模块 Y → 是否有类似的数据一致性问题？"
```

## Bug 分类决策树

```
看到 Bug → 对照 PRD 判断：

PRD 写了吗？
  ├── 没写 → 产品逻辑漏洞
  │   ├── 产品认为不需要 → 讨论：真的不需要吗？
  │   └── 产品没想到 → 记录：下次同类型需求提醒产品
  │
  └── 写了
      ├── 实现和 PRD 不一致 → 开发实现偏差
      │   ├── 开发理解错了 → PRD 表述是否清晰？
      │   └── 开发故意改了（技术限制/更好体验）→ 需要同步给产品
      │
      └── 实现了但极端场景触发 → 边界遗漏
          ├── 正常路径没问题，特定条件才触发
          └── 并发/超时/重试等非功能场景才触发
```

## 用例推动的四个层次

```
Level 1: 修 Bug                       ← 最小动作
Level 2: 修 Bug + 补一条用例            ← 点状改进
Level 3: 修 Bug + 扫同类逻辑 + 补一类用例 ← 面状改进
Level 4: 修 Bug + 提炼通用规则 → 下次 PRD 分析自动预防 ← 系统性改进
```

目标是把每个 Bug 推到 Level 3 或 4。

## 如何体现业务敏感性

在报告中，以下内容体现业务敏感性：

| 体现方式 | 例子 |
|---------|------|
| 从技术现象看到产品逻辑缺陷 | "报错不是因为代码 bug，是因为 PRD 没定义这个状态下的行为" |
| 从单点 Bug 看到同类风险 | "不仅签到有原子性问题，积分的领取/兑换/过期清理都有" |
| 从 Bug 推演出用户路径 | "用户不会只走正常路径——第1天签到→第2天卸载→第7天重装，会发生什么？" |
| 量化业务影响 | "涉及支付金额，每天约 X 笔交易，如果 X% 触发 = 每天 X 个投诉" |
| 提出可操作的规则 | "以后涉及'发奖+写状态'的需求，自动检查原子性用例是否覆盖" |

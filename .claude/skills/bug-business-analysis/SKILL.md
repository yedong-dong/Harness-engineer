# Bug 业务敏感性分析

## 使用方式

1. 用户提供 Bug 描述（文字 / 截图 / 已有的 bug.md 文件）
2. Agent 定位到对应的 PRD/项目/版本/output/ 目录
3. 读取已有的深层分析报告和测试用例，对照分析
4. 结构化记录 Bug → 业务敏感性分析 → 生成复盘报告

## 三阶段流程

```
用户提供 Bug
     │
     ▼
┌─ 阶段1：Bug 结构化记录 ─────────────────────────────────────┐
│                                                          │
│  ① 提取关键信息：                                          │
│     · 现象（用户看到什么 / 实际发生了什么）                  │
│     · 复现步骤（精确到每一步操作）                          │
│     · 环境（客户端版本 / 服务端 / 账号状态）                │
│     · 影响范围（个别用户 / 全量 / 特定条件）                │
│                                                          │
│  ② 对照 PRD 原文：                                         │
│     · 需求没写到 → 产品逻辑漏洞                             │
│     · 需求写了但实现偏差 → 开发实现漏洞                      │
│     · 需求写了也实现了，但极端场景触发 → 边界遗漏            │
│                                                          │
│  ③ 检查已有用例覆盖：                                      │
│     · 已有 .xmind 或 cases.json 中是否覆盖了此场景？        │
│     · 覆盖了但还是漏了 → 用例步骤/预期不够精确               │
│     · 完全没覆盖 → 用例设计时的盲区                         │
│                                                          │
│  ④ 写入 bugs/bug_YYYYMMDD_HHmm.md                        │
└──────────────────────────────────────────────────────────┘
     │
     ▼
┌─ 阶段2：业务敏感性分析（核心） ─────────────────────────────┐
│                                                          │
│  四维分析（详见 references/sensitivity-method.md）：        │
│                                                          │
│  ① 根因反推：这个 Bug 的根因是什么？                        │
│     · 技术层：数据结构/算法/状态机/接口哪里有问题？          │
│     · 业务层：产品逻辑本身的缺陷？                           │
│                                                          │
│  ② 测试盲区：为什么测试没发现？                              │
│     · 缺少什么类型的用例？（边界/异常/并发/状态流转）        │
│     · 用例设计时的假设是什么？假设为什么错了？               │
│                                                          │
│  ③ 业务影响：                                              │
│     · 修和不修分别对用户/指标有什么影响？                    │
│     · 如果没发现直接上线，最坏情况是什么？                   │
│                                                          │
│  ④ 关联风险：同类逻辑是否也存在类似问题？                    │
│     · 相同数据结构/状态机的地方                              │
│     · 相同开发写的其他模块                                  │
│     · 相同产品逻辑的其他入口                                │
└──────────────────────────────────────────────────────────┘
     │
     ▼
┌─ 阶段3：生成业务敏感性报告 ────────────────────────────────┐
│                                                          │
│  输出到 output/业务敏感性报告-<需求名>.md                    │
│                                                          │
│  报告结构：                                                │
│    1. Bug 总览表（一目了然）                               │
│    2. 逐 Bug 深度分析                                      │
│    3. 用例补全建议（P0/P1/P2）                             │
│    4. 知识沉淀（通用规则，可迁移到未来 PRD 分析）            │
│    5. 业务敏感性总结（基于这批 Bug，测试策略需要怎么调整）    │
└──────────────────────────────────────────────────────────┘
```

## 核心原则

1. **Bug 是礼物**：每个 Bug 都是一次免费的业务逻辑压力测试，不要只修，要复盘
2. **不追责，追根因**：不讨论"谁写的有问题"，讨论"什么逻辑/假设有问题"
3. **从 Bug 到规则**：一个 Bug → 一条检查规则 → 沉淀到 review-rules，防止同类问题
4. **用例不是目的，覆盖是目的**：补用例是手段，消除测试盲区是目标
5. **报告面向三个角色**：产品（看懂业务影响）、开发（看懂技术根因）、测试（知道怎么防）

## 报告模板

```markdown
# 业务敏感性报告：<需求名>
> 分析时间：YYYY-MM-DD | Bug 数量：N 个

## 一、Bug 总览

| # | Bug | 分类 | 根因 | 漏测原因 | 风险 |
|---|-----|------|------|---------|------|
| 1 | ... | 产品逻辑/实现偏差/边界遗漏 | ... | ... | 高/中/低 |

## 二、逐 Bug 深度分析

### Bug N：<一句话标题>

**现象**：用户做了什么 → 实际发生了什么 → 期望发生什么
**复现步骤**：1. ... 2. ... 3. ...

**根因反推**：
- 技术层：推断的技术实现 + 哪里出了问题（用伪代码表达关键逻辑）
- 业务层：产品逻辑本身的缺陷（需求文档 X 处说了 Y，但没考虑 Z）

**测试盲区**：
- 为什么没测到？缺少了什么？已有用例 gap 在哪？
**业务敏感性体现**：
- 产品为什么没想到 / 开发为什么漏掉 / 测试怎么补
**关联风险**：
- 同类逻辑：[列出可能受影响的模块]

## 三、用例补全建议

| 优先级 | 用例标题 | 覆盖的盲区 | 关联 Bug |
|--------|---------|-----------|---------|

## 四、知识沉淀

从本批次 Bug 中提取的通用规则：
- **规则 N**：涉及 XX 逻辑时，必须验证 YY（来源：Bug N）
  - 检查方法：...
  - 适用场景：...

## 五、业务敏感性总结

基于这批 Bug，当前需求的测试策略调整建议：
1. ...
2. ...
```

# Harness Engineering：测试用例生成 Pipeline

基于 Claude Code Skill 机制与 Harness Engineering 设计原则，将「PRD → 测试用例 → 平台导入」全流程固化为可复用的 Agent 编排系统。

---

## 全链路流程

```
  PRD + 技术文档 + 图片
         │
         ▼
  ┌──────────────────────────┐
  │  阶段1：合并分析 + 澄清    │
  │                          │
  │  · 四维要素提取            │
  │  · 交叉校验 PRD ↔ 技术    │
  │  ★ 暂停 → 用户确认        │
  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │  阶段2：SubAgent 并行生成  │
  │                          │
  │  · Fan-out：N 个 Agent     │
  │  · 同一条消息并行派发      │
  │  · 各自写 /tmp/cases_*.json│
  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │  阶段3：独立评估 + 回修    │
  │                          │
  │  · Evaluator 5 维度评分   │
  │  · 通过 → 导出            │
  │  · 不通过 → 回修（最多3轮）│
  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │  阶段4：导出 + 平台导入    │
  │                          │
  │  · .xmind 导出            │
  │  · MCP 分批导入平台        │
  └──────────────────────────┘
```

仅 1 个人工节点：阶段1 末尾的澄清确认。其余全自动流转。

## 架构设计：三层分离

```
  ┌──────────────────────────────────────────────────────────────┐
  │ 调度层（主 Agent）                                            │
  │                                                              │
  │  PRD分析 → 四维提取 → 交叉校验 → 澄清 → 模块拆分 → 派发       │
  │                                                              │
  │  ★ 1 条消息并行派发 N 个 SubAgent                             │
  │  ★ 收集结果 → 合并去重 → 交 Evaluator                        │
  └───────────────────────────┬──────────────────────────────────┘
                              │
                              ▼
  ┌──────────────────────────────────────────────────────────────┐
  │ 执行层（SubAgent 池）                                         │
  │                                                              │
  │  SubAgent-1    SubAgent-2    SubAgent-3    ...   SubAgent-N  │
  │  ──────────    ──────────    ──────────          ──────────  │
  │  模块A·8条     模块B·11条    模块C1·9条           模块N·N条   │
  │      │              │             │                  │       │
  │      └──────────────┴─────────────┴──────────────────┘       │
  │                         │                                    │
  │               /tmp/cases_*.json                              │
  │                                                              │
  │  每个 SubAgent 收到：PRD片段 + 技术摘要 + 约束 + 确认决策      │
  │  互不依赖，完全并行                                           │
  └───────────────────────────┬──────────────────────────────────┘
                              │
                              ▼
  ┌──────────────────────────────────────────────────────────────┐
  │ 质控层（Evaluator SubAgent）                                  │
  │                                                              │
  │  输入：PRD 全文 + cases.json                                  │
  │  ★ 上下文隔离：不接触生成过程                                 │
  │                                                              │
  │  5 维度评分                                                   │
  │  ┌────────────┬──────────┬──────┬───────────────────────┐     │
  │  │ 功能覆盖    │ ≥ 80%    │ 最高  │ Feature 都有 P0/P1     │     │
  │  │ 规则覆盖    │ ≥ 80%    │ 高    │ 业务规则都有验证 case  │     │
  │  │ 边界/异常   │ ≥ 60%    │ 中    │ 边界值+并发+幂等       │     │
  │  │ 优先级分布  │ ≥ 70%    │ 中    │ P0:15%-40% 分布合理   │     │
  │  │ 可执行性    │ ≥ 80%    │ 低    │ 步骤可操作预期可验证   │     │
  │  └────────────┴──────────┴──────┴───────────────────────┘     │
  │                                                              │
  │  全部通过 ✓ → 放行导出                                        │
  │  不通过   ✗ → regenerate_hint → 调度层回修 → 重新评估         │
  └───────────────────────────┬──────────────────────────────────┘
                              │
                              ▼
                        .xmind 导出
                      平台导入（可选）
```

各层职责清晰：**调度层管做什么、执行层管怎么做、质控层管做得对吗**。

## SubAgent 并行协作：Fan-out / Fan-in

```
                         ┌─ SubAgent-1（模块A·8条）──┐
                         ├─ SubAgent-2（模块B·11条）─┤
  主Agent（拆解 + 派发）──┼─ SubAgent-3（模块C1·9条）─┼── 合并去重 ── Evaluator
                         ├─ SubAgent-4（模块C2·7条）─┤
                         └─ SubAgent-5（模块D·9条）──┘

  Fan-out（发散）                Fan-in（汇合）
  ════════════                 ════════════
  1 条消息 → N 个 Agent         N 组输出 → 1 份 cases
  并行执行，互不阻塞            自动去重 + 字段校验
```

### 拆分策略（负载均衡）

```
  · 按模块树一级分组拆分
  · 单模块预估 > 12 条 → 强制再拆
  · 单 Agent 总量 > 20    → 强制再拆（即使各子模块都不超 12）
  · 拆完后核对：各 Agent 估价应尽量接近
```

### 每个 SubAgent 收到的上下文

```
  · PRD 模块专属片段      —— 只给和自己相关的
  · 技术摘要（分级过滤）   —— 状态机/缓存key/边界数值，不含代码路径
  · 交叉校验差异表        —— PRD ↔ 技术文档不一致项的决策结论
  · 约束限制              —— 用户指定的范围（只测XX / 不测XX）
  · 用户确认决策          —— 澄清阶段的回答
```

## 评估机制：独立盲评 + 回修循环

```
  cases.json
       │
       ▼
  ╔═════════════════╗
  ║  Evaluator      ║  ← 独立上下文（仅 PRD + cases.json）
  ║  5 维度评分      ║
  ╚═══╤═════════╤═══╝
      │         │
   通过 ✓     不通过 ✗
      │         │
      │         ▼
      │     regenerate_hint（精确回修提示）
      │         │
      │         ▼
      │     主 Agent 按提示补充 case
      │         │
      │         ├─ attempt ≤ 3 → 重新评估
      │         └─ attempt > 3 → 标记「人工复核」，不阻塞导出
      │                          │
      └─────────┬────────────────┘
                ▼
              导出
```

### 为什么 Evaluator 独立于 Generator

Generator 的上下文包含生成全过程的中间信息；Evaluator 只看到输入（PRD）和输出（cases.json）。上下文不互通，Evaluator 不受 Generator 思维惯性影响，判断更客观。

Anthropic 2025 Harness Design 的核心发现：**让一个 Agent 自我评价 → 它倾向于自信地赞美自己的平庸作品。分离出一个独立 Evaluator → 远比调教自检 Prompt 更有效。**

## 技术优势

### 架构层面

- **Fan-out/Fan-in 并行模式**：单条消息派发 N 个 SubAgent，并行产出，互不阻塞。模块越多效率优势越明显
- **三层分离**：调度、执行、质控职责清晰，每层上下文独立，不互相污染
- **负载均衡拆分**：自动按模块规模拆分，避免单个 Agent 过载或空转

### 质量层面

- **独立盲评**：Evaluator 上下文与 Generator 完全隔离，不走「我觉得还行」的过场
- **5 维度量化**：功能覆盖 / 规则覆盖 / 边界异常 / 优先级分布 / 可执行性，各有硬阈值
- **精确回修**：每个 gap 附带 `regenerate_hint`，Generator 直接按提示修，不是笼统的「请检查」
- **3 轮兜底**：超时自动标记人工复核，不阻塞流程

### 工程化层面

- **全流程 SOP 固化**：PRD → 分析 → 澄清 → 生成 → 评估 → 导出 → 导入，封装为可复用 SKILL.md
- **零人工转写**：从非结构化 PRD 文字到标准化 .xmind，仅 1 个人工确认节点
- **交叉校验**：PRD ↔ 技术文档差异自动发现，附带默认假设直接列澄清问题
- **格式严格校验**：priority / platform / steps 字段自动校验，不合规直接拦截

### 扩展性

- **模块化 SubAgent 池**：新增模块只需增加 SubAgent 实例，不改变架构
- **评估标准可配置**：5 维度阈值可按项目特点调整
- **平台导入可插拔**：xmind-import 作为独立 Skill，不耦合在主流程中

## 与 Harness Engineering 设计原则的对照

| 原则（来自 Anthropic/OpenAI） | 本系统中的落地 |
|---|---|
| 增量推进，不一蹴而就 | 4 阶段流水线，每阶段有明确的输入/输出约定 |
| 环境作为共享记忆 | 阶段1 落盘 `需求信息.md`；阶段2 写 `/tmp/cases_*.json`；阶段3 产出 `workflow.md` |
| 生成与评估分离 | Generator（阶段2）与 Evaluator（阶段3）上下文完全隔离 |
| 主观判断变可量化标准 | 5 维度硬阈值，不依赖「感觉覆盖全了」 |
| 每个组件赌的是模型能力的短板 | 评估维度按模型弱点设计（越弱越需要 Evaluator） |
| 模型升级后拆掉过渡组件 | Evaluator 作为可插拔模块，模型能力提升后可降低阈值或移除 |

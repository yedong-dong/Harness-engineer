## 通用方法论：三步分析法

面对任何岗位，用三个问题找到 Agent 切入点：

```
第一问：这个岗位的「输入」是什么？
  ├── 产品经理：想法、数据、竞品信息、用户反馈
  ├── 开发工程师：需求文档、接口定义、排期计划
  ├── 测试工程师：PRD、技术方案、接口文档
  ├── 数据分析师：业务问题、SQL 需求、原始数据
  ├── 项目经理：任务看板、变更记录、会议内容
  └── 运营：活动目标、竞品动态、用户反馈

第二问：什么工作「量大、规则明确、重复」？
  ├── 量大 + 规则明确 + 重复 → Agent 可替代度高 ✓
  ├── 量大 + 规则模糊 + 需要判断 → Agent 辅助，人决策 △
  └── 量小 + 规则模糊 + 创造性 → 留给人的核心价值 ✗

第三问：Agent 的输出能直接用吗？还是需要人把关？
  ├── 可直接用 → 全自动（如：自动生成日报、自动打标签）
  ├── 需审核 → 半自动（如：代码生成后人工 Review）
  └── 仅参考 → 辅助（如：竞品分析报告标注信源，人验证）
```

这三个问题的答案直接决定了 Agent 在该岗位的落地深度。

## 六岗位速览对比

| 维度 | 产品经理 | 开发工程师 | 测试工程师 | 数据分析师 | 项目经理 | 运营 |
|------|---------|-----------|-----------|-----------|---------|------|
| **Agent 可替代度** | 40% | 50% | 60% | 55% | 35% | 45% |
| **核心 Agent 角色** | 分析+生成 | 生成+审查 | 生成+评估 | 查询+分析 | 追踪+汇总 | 生产+分类 |
| **典型输入** | 想法/数据 | 需求/接口 | PRD/方案 | 问题/数据 | 看板/会议 | 目标/反馈 |
| **典型输出** | PRD/报告 | 代码/Review | 用例/脚本 | SQL/报表 | 日报/预警 | 内容/配置 |
| **落地难度** | 中 | 高 | 低 | 中 | 低 | 低 |
| **已有落地案例** | 无 | 无 | **有（本项目的 prd-testcase-xmind）** | 无 | 无 | 无 |

> **可替代度说明**：指该岗位中「量大+规则明确+重复」的工作占比，不代表岗位可被替代。判断、创造、跨部门协调等工作仍然是人的核心价值。

## Agent 架构模式速查

这些模式来自本项目已在测试岗位跑通的架构，可迁移到其他岗位：

### 三层泳道架构

```
调度层（主 Agent）  → 任务拆分、派发、结果汇总
执行层（SubAgent 池）→ 并行处理各自任务
质量层（评估器）    → 独立评分、打回修正、控制质量门
```

参考：[swimlane-architecture.md](../workflow_reference/swimlane-architecture.md)

### 并行派发（Fan-out Fan-in）

```
主Agent ──┬── SubAgent-1 ── 处理模块A ──┐
           ├── SubAgent-2 ── 处理模块B ──┤
           └── SubAgent-3 ── 处理模块C ──┘
                                          ↓
                                     结果合并
```

负载均衡：单模块超过阈值（如 12 条用例）时强制拆分。

参考：[fan-out-fan-in.md](../workflow_reference/fan-out-fan-in.md)

### 生成器-评估器分离

```
Generator ──→ 生成产物 ──→ Evaluator（独立上下文，不知道 Generator 思路）
                              ↓
                     评分 + 精确修改提示
                              ↓
                     不通过 → 回修（最多 N 轮）
                              ↓
                     通过 → 交付
```

参考：[generator-evaluator-separation.md](../workflow_reference/generator-evaluator-separation.md)

## 通用落地路径框架

无论哪个岗位，Agent 落地都遵循同一递进路径：

```
Phase 1: 最小可用（1周）
  ├── 选 1 个最痛的场景
  ├── 不写代码，纯 Prompt + 上下文
  ├── 跑通端到端，哪怕结果是 60 分
  └── 标记：哪些环节 Agent 表现好/差

Phase 2: 规模化（1个月）
  ├── 接入真实数据源（MCP / API / 数据库只读）
  ├── 引入多层 Agent 架构（调度+执行+评估）
  ├── 定义质量门控标准
  └── 沉淀为 Skill / 可复用配置

Phase 3: 持续优化（长期）
  ├── 收集人工修正 → 反向优化 Prompt
  ├── 效果量化：时间、质量、覆盖率
  ├── 扩展场景：从 1 个痛点到 N 个
  └── 知识沉淀：出方法论、培训他人
```

## 如何使用这些文档

### 如果你是一个岗位的从业者

1. 先读该岗位的角色画像，确认和自己的实际工作吻合度
2. 对照痛点列表，看哪些你也痛
3. 直接跳到「落地路径 → Phase 1」，本周就能跑通一个 Demo
4. 按 Prompt 模板开箱即用，调优即可

### 如果你是团队管理者

1. 先看「六岗位速览对比表」，了解各岗位的 Agent 可替代度
2. 选可替代度高 + 落地难度低的岗位先试点（推荐：测试 > 运营 > 项目经理）
3. 用收益预估数据做 ROI 说服
4. 注意每个岗位的「风险边界」章节，避免踩坑

### 如果你是 AI 工具开发者

1. 「Prompt 模板」章节可快速了解每个岗位的需求形态
2. 「Agent 优化地图」章节展示了各岗位的理想状态
3. 「已有落地案例」标注了哪些已验证、哪些待构建

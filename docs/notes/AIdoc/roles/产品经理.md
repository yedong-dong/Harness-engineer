# 产品经理 × Agent 深度应用指南

> 状态：待验证 | 基于三步分析法推理，欢迎落地后反馈迭代

---

## 1. 角色画像

### 核心职责

产品经理负责定义产品方向、设计功能方案、推动落地。核心工作：用户与市场洞察、需求规划、PRD 撰写、需求评审、上线后的效果验证。

### 典型的一天

```
09:30  看数据看板：昨日核心指标（DAU、留存、转化率）
10:00  用户反馈群/App Store 评论/客服工单，标记有价值的需求
10:30  开需求评审会：和开发/测试对齐下一版需求
11:30  散会后根据评审意见修改 PRD
14:00  写新需求 PRD：流程图、交互说明、埋点需求
16:00  和设计师对交互方案
17:00  竞品体验：竞品更新了什么
18:00  处理各群里的临时确认消息（"这个边界怎么处理？""这个文案定了吗？"）
```

### 关键 KPI

- 需求交付量（版本需求数）
- 需求质量（评审返工次数）
- 功能上线后的数据表现（DAU/转化/留存）
- 需求到上线的周期

### 与上下游的依赖

```
用户反馈/数据 ──→ 产品经理 ──PRD──→ 开发工程师
  竞品分析                  │
  业务目标                  ├──交互稿──→ 设计师
                            ├──埋点需求──→ 数据团队
                            └──需求评审──→ 测试工程师
```

## 2. 核心痛点深度分析

### P0-1：PRD 撰写耗时大，从「想清楚」到「写清楚」有巨大损耗

- **现状**：一个中等复杂度的需求（如"新增用户等级体系"），产品经理通常在脑中有较清晰的思路。但把思路转化为结构化的 PRD（含业务背景、流程图、交互说明、异常处理、埋点需求），需要 4-8 小时纯写文档的时间。这期间大量精力花在「表述」而非「思考」上。
- **耗时估算**：每周 15-25 小时（占 30-50% 工作量）
- **痛苦根源**：
  - 文字表述是确定的、规范的——"用户点击按钮后，若未登录则跳转登录页"这类描述几乎有固定模板
  - 流程图、状态机、逻辑分支梳理是结构化工作，但绘图工具操作耗时
  - 最痛苦的是：你脑子想完了，手还要花三倍时间写完
- **Agent 可替代性分析**：
  - 产品经理口述/列要点 → Agent 扩展为结构化 PRD ✓
  - 生成流程图描述（ASCII/Mermaid）→ Agent 可自动生成 ✓
  - 梳理异常分支 → Agent 可按模板穷举 ✓
  - 业务决策（"等级门槛定 100 还是 200？"）→ 需要人基于数据和策略判断 ✗

结论：产品经理可以「说 PRD」而不是「写 PRD」，Agent 承担 70% 的文案和格式化工作。

### P0-2：需求评审反复修改，信息对齐成本高

- **现状**：评审会上，开发提出技术约束、测试提出边界场景、设计师提出交互矛盾。产品经理会后修改 PRD，再约二次评审。一轮需求常常 2-3 次评审才能定稿。
- **耗时估算**：每个需求 2-4 小时纯会议 + 2-3 小时改文档
- **痛苦根源**：产品经理一个人很难穷举所有异常场景和边界条件，而这些恰恰是开发和测试最关心的。
- **Agent 可替代性分析**：
  - 评审前先让 Agent 模拟开发/测试/设计视角审查 PRD → 提前发现 60% 的问题 ✓
  - Agent 按「合法性校验」模板穷举异常分支 → 补充 PRD 的异常处理章节 ✓

### P1-1：竞品分析占时间但不一定有洞察

- **现状**：定期体验竞品、截图、整理功能对比表。大部分时间是操作性的（下载更新、截图、画表格）。
- **耗时估算**：每周 3-6 小时
- **痛苦根源**：信息收集 80% 时间，分析洞察只占 20%——但只有 20% 有价值。
- **Agent 可替代性分析**：
  - Agent 爬取竞品更新日志、用户评价、应用商店描述 → 自动生成对比报告 ✓
  - 按功能维度自动归类、生成差异分析 ✓
  - 但不能替代产品经理亲自体验的「手感」✗

### P1-2：用户反馈信息量大、分类困难

- **现状**：用户反馈来自 App Store 评论、客服工单、用户群、NPS 问卷，每日几十到几百条。手工分类（Bug/需求/体验/咨询）和去重极耗时。
- **耗时估算**：每周 3-5 小时
- **Agent 可替代性分析**：
  - 自动分类（Bug/需求/体验/咨询）+ 按主题聚类 ✓
  - 自动去重（相同问题合并计数）✓
  - 提取高频关键词并生成趋势报告 ✓

### P2：埋点需求编写重复且易遗漏

- **现状**：每个需求都要写埋点文档（页面曝光、按钮点击、事件参数），格式固定但繁琐。
- **耗时估算**：每个需求 0.5-1 小时
- **Agent 可替代性分析**：从 PRD 中提取可埋点的事件 → 按模板生成埋点文档 ✓

│                      │                                                │

│                                                                      │

### Before vs After

```
Before（一个需求全流程 12h）:
  想思路(2h) → 写PRD(5h) → 评审+修改(3h) → 埋点(1h) → 竞品(1h)

After（Agent+人 6h）:
  口述要点(0.5h) → Agent生成PRD(2min) → 人修改(1.5h)
  → Agent预审(1min) → 正式评审+修改(2h) → Agent生成埋点(1min) → 人确认(0.5h)
  → Agent竞品周报(自动)
```

## 4. 落地路径

### Phase 1：口述 → PRD 初稿（1 周）

**做什么**：
1. 训练一个「你的 PRD 模板」——把你觉得写得好的 2-3 份历史 PRD 喂给 Agent，让它学会你的风格和结构
2. 下次写新需求时，不用打字——用语音或要点列表描述功能
3. Agent 生成结构化 PRD，你只做修改和补充

**用什么工具**：
- Claude Code / ChatGPT / 任何支持长上下文的 LLM
- 预先准备好的 PRD 模板 Markdown

**预期收益**：
- PRD 撰写时间：5h → 2h
- 格式/结构 100% 规范（Agent 不会忘章节）

**最小 Demo**：
```
你是一位资深产品经理。我接下来会口述一个新功能的需求要点，
请你帮我扩展为一份完整的 PRD 文档。

【PRD 结构要求】
1. 需求背景（为什么要做、数据支撑）
2. 目标用户（Who、What、Why）
3. 功能详述（主流程 + 异常分支）
4. 交互说明（关键页面的元素和跳转逻辑）
5. 埋点需求（需要采集的事件和参数）
6. 验收标准（可测试的 Checklist）

【参考我之前的 PRD 风格】
{粘贴 1-2 份历史 PRD}

现在，请听我的描述：
{口述/要点列表}
```

### Phase 2：评审前置 + 用户反馈自动化（1 个月）

**做什么**：
1. 评审前置：每次评审前让 Agent 用开发/测试/设计视角审查一遍，修改后再进入正式评审
2. 用户反馈自动化：导出 App Store 评论 + 客服工单，让 Agent 分类聚类，每周出报告

**关键挑战**：
- 用户反馈需要 API 或手动导出（App Store Connect API / 客服系统导出）
- Agent 的审查质量取决于 Prompt 的「角色设定」是否精准

**预期收益**：
- 评审轮次：2-3 轮 → 1-2 轮
- 用户反馈处理：5h/周 → 1h/周

### Phase 3：数据驱动的需求决策辅助（长期）

**做什么**：
1. 接入数据看板（只读），Agent 读取核心指标变化并生成解读
2. Agent 帮你追踪需求上线后的实际效果，对比预期目标
3. 需求优先级判断辅助（结合影响面、开发成本、业务目标）

**预期收益**：
- 需求 ROI 可量化，减少拍脑袋决策

## 5. Prompt 模板

### 模板 1：口述转 PRD

```
你是一位资深产品经理。请根据我的描述，生成一份完整的需求文档。

【要求】
- 语言风格：简洁直接，不要官腔
- 每个功能必须包含：正常流程 + 至少 3 个异常分支
- 用 ASCII 画出核心流程图

【我的描述】
{口述内容或要点列表}
```

### 模板 2：多角色预评审

```
请分别从以下三个角色审查这份 PRD，给出具体的修改建议：

【开发视角】
- 哪里的技术实现可能存在歧义？
- 哪些功能点的技术成本可能被低估？
- 有没有技术上不可行或需要折中的地方？

【测试视角】
- 哪些边界场景和异常分支没有覆盖？
- 状态流转是否完整？有没有断开的状态？
- 并发/网络异常/数据一致性是否有考虑？

【设计视角】
- 交互逻辑是否有前后矛盾？
- 用户的操作路径是否流畅？

【PRD 内容】
{粘贴 PRD}
```

### 模板 3：竞品功能对比

```
请帮我做一份竞品功能对比分析。

【我方产品】{产品名称和当前版本功能列表}

【竞品清单】
- 竞品A：{名称}
- 竞品B：{名称}

请从以下维度对比：
1. 核心功能差异（表格形式）
2. 交互体验差异（关键页面）
3. 定价策略差异
4. 用户评价中的高频关键词（好评/差评各 Top 5）

【信息来源】：请标注每条信息的来源（官方更新公告/用户评价/媒体报道）。
```

### 模板 4：用户反馈分类聚类

```
以下是 {时间段} 的用户反馈（{N} 条），请完成：

1. 按类型分类：Bug / 功能需求 / 体验优化 / 咨询 / 其他
2. 同一问题的反馈合并去重，标注出现次数
3. 提取高频关键词 Top 10
4. 标注需要紧急处理的 P0 问题（影响核心功能 / 大规模用户受影响）

【用户反馈】
{粘贴反馈列表}
```

### 模板 5：埋点文档自动生成

```
根据以下需求文档，生成一份埋点需求表：

【埋点格式】
| 事件ID | 事件名称 | 触发时机 | 参数列表 | 参数说明 | 上报时机 |

【覆盖要求】
- 所有页面曝光事件
- 所有可点击元素的点击事件
- 关键业务流程的节点事件
- 异常情况的事件（如加载失败、支付取消）

【PRD】
{粘贴 PRD}
```

### 模板 6：需求变更影响范围

```
我修改了一个需求中的部分逻辑（见下方），请帮我分析这个变更的影响范围：

【变更描述】
{描述改了什么}

【完整 PRD】
{粘贴完整 PRD}

请分析：
1. 哪些已有功能点受此变更影响
2. 是否有交互流程需要重新梳理
3. 埋点是否需要调整
4. 建议通知哪些同事（开发/测试/设计/运营）
```

### 模板 7：数据指标解读

```
以下是今日核心数据，请帮我做解读：

【数据】
- DAU：{数值}（环比 {+/-x%}）
- 新增用户：{数值}（环比 {+/-x%}）
- 留存率（次日/7日/30日）：{数值}
- 核心转化率：{数值}（环比 {+/-x%}）

请分析：
1. 哪个指标变化最显著（可能有异常）
2. 可能的原因分析（标注确定性高低）
3. 建议优先关注的方向
```

## 6. 收益预估 & 风险边界

### 量化收益

| 环节 | 纯人工 | Agent + 人 | 节省比例 |
|------|--------|-----------|---------|
| PRD 撰写（单需求） | 4-6h | 1.5-2.5h | 50-60% |
| 评审前自检 | 无（依赖评审会发现） | 10min | 减少 1 轮评审 |
| 竞品分析（周） | 4h | 1h | 75% |
| 用户反馈分类（周） | 4h | 0.5h | 85% |
| 埋点文档（单需求） | 1h | 15min | 75% |
| **每周总计** | **~25h** | **~10h** | **~60%** |

### 不可做的边界

```
✗ Agent 不能替代人的地方：
├── 业务决策：这个功能做不做、优先级怎么排（数据可以提供，判断必须人做）
├── 用户同理心：对用户需求的深层理解（Agent 只能基于文字，没有真实体验）
├── 跨部门协调：说服开发接受需求、争取资源（人际关系和信任，Agent 无法建立）
├── 产品愿景：产品的长期方向和定位（战略思考，不是分析）
└── 灰度决策：当一个功能对 90% 用户好但对 10% 用户造成困扰时的取舍

✗ 给 Agent 的限制：
├── 竞品分析信息必须标注来源，不可凭空捏造竞品功能
├── 用户反馈涉及隐私数据（手机号、ID）需脱敏后再喂给外部 Agent
└── PRD 是内部机密文档，使用本地 Agent 而非上传到公有云服务
```

### 常见陷阱

1. **过度信任 Agent 的分析**：Agent 的竞品分析可能把猜测当事实，必须逐个验证来源。
2. **PRD 千篇一律**：如果完全依赖 Agent 模板，所有 PRD 会看起来一样——失去对每个需求独特性的思考。
3. **跳过亲自体验**：Agent 分析竞品不能替代你亲自下载用一用——手感、卡顿、微交互只有亲身体验能感知。
4. **忽视视觉表达**：Agent 擅长文字，但不擅长画交互稿——流程图可以 ASCII，界面交互还是需要设计工具。
5. **用户反馈的虚假信号**：Agent 聚类可能把不同类型的反馈合并，或者遗漏少数但重要的反馈。

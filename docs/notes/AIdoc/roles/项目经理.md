# 项目经理 × Agent 深度应用指南

> 状态：待验证 | 基于三步分析法推理，信息汇总类工作 Agent 可替代度高

---

## 1. 角色画像

### 核心职责

项目经理负责保障项目按时按质交付。核心工作：进度跟踪、风险管理、资源协调、会议组织、信息同步。项目经理是信息的「枢纽」——从各个渠道汇聚信息，处理后分发给对应的人。

### 典型的一天

```
09:15  看 Jira/TAPD：昨天任务的完成情况，有没有延期
09:30  站会：听每个人的进展和阻塞
10:00  会后处理站会上暴露的问题（张三的任务被李四阻塞了 → 去协调）
11:00  更新项目看板、写日报
14:00  参加跨部门同步会（和产品/运营/测试对齐版本排期）
15:00  风险排查：下周五发版，还有 3 个需求没提测，能赶上吗？
16:30  做排期：和开发 Leader 确认下个迭代的需求范围
17:00  处理临时问题：线上告警 → 拉人排查 → 跟踪进展
19:00  写日报/周报（如果还没写）
```

### 关键 KPI

- 项目按时交付率
- 需求交付周期（从评审到上线）
- 延期预警提前发现率
- 资源利用率（有没有人长期空转或过载）

### 与上下游的依赖

```
产品经理 ──需求+优先级──→ 项目经理 ──排期+任务──→ 开发/测试工程师
  管理层  ──目标+Deadline──→    │           ──进度+风险──→ 管理层
                              ├──阻塞协调──→ 各团队 Leader
                              └──信息同步──→ 所有干系人
```

项目经理的核心工作是**信息处理**，而非信息创造——这正是 Agent 最擅长的领域。

## 2. 核心痛点深度分析

### P0-1：信息收集碎片化，追踪成本极高

- **现状**：项目的真实进展分散在多个工具中。要看一个需求走到哪了，需要：打开 Jira/TAPD 看任务状态 → 打开代码仓库看分支/MR → 打开测试平台看用例执行 → 在群里问当事人。每次信息收集花 20-30 分钟，而一天可能要收集 5-10 次。
- **耗时估算**：每周 10-15 小时在「查进展」上
- **痛苦根源**：
  - 工具之间没有自动联动（Jira 任务关闭 ≠ 代码已合并 ≠ 测试已通过）
  - 信息的权威性不一致：Jira 显示「已完成」，但群里当事人说「还有个 Bug 在修」
  - 人工拼凑信息不仅慢，还容易漏
- **Agent 可替代性分析**：
  - Agent 同时读 Jira/TAPD、Git 仓库、CI/CD、测试平台 → 自动拼凑每个需求的真实状态 ✓
  - 自动生成「进度看板」而不是手工维护 ✓
  - 跨工具状态一致性校验（Jira 说 Done 但 MR 还没合）→ Agent 自动标出 ✓

结论：项目经理的主要「查进展」工作可以由 Agent 自动化，人只需要处理 Agent 标出的异常。

### P0-2：日报/周报是重复的机械劳动

- **现状**：日报/周报的内容（谁做了什么、什么完成了、什么延期了、为什么延期）并非凭空创造——它们来自 Jira 状态变更、Git 提交记录、站会上的口述。但项目经理需要手工收集、整理、格式化。
- **耗时估算**：日报 15-30 分钟/天，周报 2-3 小时/周。每周合计 5-7 小时。
- **Agent 可替代性分析**：
  - Agent 读 Jira → 提取过去 N 天的状态变更 → 自动生成日报/周报 ✓
  - Agent 读 Git → 提取合并记录和变更摘要 ✓
  - 按模板格式化输出 → 人只补充「需要特别说明」的部分 ✓

### P1-1：风险识别依赖经验，新手 PM 容易遗漏

- **现状**：有经验的 PM 能一眼看出「这个需求的进度不对，可能要延期」，靠的是：看任务的 Burn-down 趋势、看关键路径上的任务是否 delay、看阻塞项堆积情况。新手 PM 通常等延期已经发生了才发现。
- **耗时估算**：有经验 PM 的风险感知差不多实时，新手 PM 可能延迟 2-3 天
- **Agent 可替代性分析**：
  - Agent 自动计算：每个需求的计划 vs 实际进度偏差 ✓
  - 自动识别关键路径上是否有任务延期 ✓
  - 当异常模式出现时（如连续 3 天无进展的任务），自动预警 ✓
  - 但不了解团队成员的个性、能力差异等「软信息」✗

### P1-2：跨部门信息同步重复又容易失真

- **现状**：同样一件事——「XX 功能延期到下周三」——需要同步给产品（影响排期）、测试（影响用例执行计划）、运营（影响活动上线时间）。每个群/邮件都要说一遍，且每次转述可能丢失细节。
- **耗时估算**：每周 3-5 小时花在多渠道同步上
- **Agent 可替代性分析**：
  - 一次输入变更信息 → Agent 按各受众生成不同版本的同步通知 ✓
  - 自动推送到对应群/邮件/文档 ✓

### P2-1：会议纪要 = 人到场 + 认真听 + 快速记 + 会后整理

- **现状**：PM 是绝大多数会议的常驻人员，因为需要记录待办和决策。但「记录」这件事本身不产生价值——价值在「决策」和「待办执行」。
- **Agent 可替代性分析**：
  - 会议录音转文字 → Agent 提取待办（TODO）、决策（Decision）、信息点（Info）✓
  - 按人分配待办并自动创建对应任务单 ✓

### P2-2：资源负载分析靠感觉

- **现状**：PM 大致知道每个人在忙什么，但很难精确回答「张三这周还有精力再接一个小需求吗？」这类问题。
- **Agent 可替代性分析**：
  - Agent 从 Jira 提取每个人的当前任务量 + 历史完成速度 → 计算剩余容量 ✓
  - 生成团队负载热力图 ✓

### Before vs After

```
Before（每天 3h「搬砖」）:
  查Jira(0.5h) → 问聊天记录(0.3h) → 写日报(0.3h)
  → 更新看板(0.3h) → 同步消息给各群(0.3h) → 写会议纪要(0.5h)

After（Agent 自动化 0.3h 人确认）:
  Agent自动出日报(0) → 人看一眼补充(0.1h)
  → Agent自动更新看板(0) → Agent自动风险告警(0)
  → 会议录音→Agent出纪要(0.1h确认)
```

## 4. 落地路径

### Phase 1：日报/周报自动化（3 天）

**做什么**：
1. 在 Jira/TAPD 中导出最近一周的任务变更记录
2. 喂给 Agent + 你的日报/周报模板
3. Agent 生成初稿，你只做补充和确认

**用什么工具**：
- Jira/TAPD MCP 或 API 导出
- Claude Code / ChatGPT + 模板

**最小 Demo**：
```
你是一个项目经理。以下是本周的 Jira 任务变更数据和 Git 合并记录。

【本周任务变更】
{从 Jira 导出的状态变更列表，包含：任务标题、负责人、原状态→新状态、变更时间}

【Git 合并记录】
{本周合并的 MR 列表，包含：标题、作者、合并时间}

【日报/周报模板】
{你的周报模板}

请生成周报初稿，包括：
1. 本周完成的需求
2. 下周计划
3. 风险项（本周有延期的任务）
4. 需要关注的问题

对于你无法确定的描述，用 [待确认] 标注，我会补充。
```

**预期收益**：
- 日报/周报时间：5-7h/周 → 1h/周
- 信息完整度提升（Agent 不会遗漏 Jira 里有的变更）

### Phase 2：进度看板自动聚合（1 个月）

**做什么**：
1. 打通 Jira/TAPD + Git + CI/CD + 测试平台的只读访问
2. Agent 每 2 小时自动拉取各平台数据，生成统一进度看板
3. 异常状态自动告警（Jira 和 Git 状态矛盾、关键路径延期等）

**关键挑战**：
- 需要各平台的 API/MCP 权限
- Jira 工作流自定义度高，需要让 Agent 理解自定义状态含义
- 信息刷新频率需要平衡实时性和 API 调用量

**预期收益**：
- 进度追踪时间：10h/周 → 2h/周
- 延期发现提前 1-2 天

### Phase 3：智能 PM 助手（长期）

**做什么**：
1. 会议录音 → 自动纪要 + 自动创建待办
2. 资源负载分析：每人的任务饱和度和剩余容量
3. 版本复盘自动生成：从历史数据中总结本版本的问题和亮点

**预期收益**：
- 信息同步时间降低 70%
- PM 可以同时管理更多项目

## 5. Prompt 模板

### 模板 1：日报自动生成

```
你是一个项目经理。请根据以下数据生成今日日报：

【今日 Jira 变更】
{导出今日状态变更}

【阻塞项】
{当前所有标记为 Blocked 的任务}

【明日计划】
{各成员口头同步或Jira中标记的下一个任务}

日报格式：
1. 今日完成（按人分组）
2. 进行中（进度正常的 + 进度有风险的分类）
3. 阻塞项（阻塞原因 + 需要谁来解决）
4. 明日关键事项（最多 3 条）
```

### 模板 2：周报自动生成

```
你是一个项目经理。请根据以下数据生成本周周报：

【本周完成的 MR】
{Git 本周合并记录}

【本周 Jira 变更】
{Jira 状态变更记录，按时间排序}

【上周遗留问题进展】
{上周周报中列出的风险项}

周报格式：
1. 版本整体进度（燃尽图文字版：计划 vs 实际）
2. 各需求进展（已完成/进行中/有风险）
3. 风险项（需要管理层关注的问题）
4. 下周计划
```

### 模板 3：风险预警分析

```
你是一个项目经理。以下是当前版本的任务数据：

【版本信息】
- 版本名称：{版本号}
- 发版日期：{日期}
- 当前距离发版：{X} 天

【任务状态】
{任务列表，含：标题、负责人、计划开始/结束、实际进度百分比、状态}

请分析：
1. 哪些任务有延期风险（基于当前进度和剩余时间的偏差）
2. 关键路径上是否有延迟任务
3. 阻塞项是否在堆积
4. 建议给管理层的预警（如果有）
```

### 模板 4：会议纪要提取

```
你是一个会议记录员。以下是会议的文字转录，请生成结构化纪要：

【会议信息】
- 主题：{主题}
- 参与人：{名单}

【会议转录】
{转录文本}

请按以下格式输出：
1. 决策（D）
   - 决策内容 + 决策人
2. 待办（TODO）
   - 事项 + 负责人 + 截止时间
3. 信息同步（I）
   - 需要转达给未参会人员的信息
4. 下次会议议题建议
```

```

【受众 1：管理层】

【受众 2：产品经理】

【受众 4：运营】

```
你是一个项目经理。以下是团队成员的当前任务分配：

【团队成员任务】
{按人列出的任务清单，含：任务名、预估工时、已完成比例、Deadline}

请分析：
1. 每个人的当前负载（饱和度百分比）
2. 谁有富余容量可以接新任务

4. 未来 2 周的人员瓶颈预判

### 模板 7：版本复盘初稿

```
你是一个项目经理。请根据以下数据生成本版本的复盘初稿：

【版本数据】
- 计划需求数：{N}，实际完成：{M}
- 计划工时：{H}，实际工时：{H_actual}
- 提测时间偏差：{延期天数}
- 线上 Bug 数：{N_bugs}

【过程记录】
{版本周期内的关键事件：需求变更、线上事故、人员变动等}

复盘格式：
1. 版本概览（一句话总结）
2. 做对了什么（Keep）
3. 哪里可以改进（Improve）
4. 下个版本的建议（Action）
5. 感谢（对团队成员的亮点表扬）
```

## 6. 收益预估 & 风险边界

### 量化收益

| 环节 | 纯人工 | Agent + 人 | 节省比例 |
|------|--------|-----------|---------|
| 日报（每天） | 30min | 5min | 85% |
| 周报（每周） | 2-3h | 20min | 85% |
| 进度追踪（每周） | 10h | 2h | 80% |
| 会议纪要（每次） | 40min | 5min（确认） | 85% |
| 信息同步（每周） | 4h | 0.5h | 85% |
| **每周总计** | **~20h** | **~4h** | **~80%** |

> 注意：PM 的工作中信息汇总占比最高，因此 Agent 可替代的时间比例在六岗位中排名第一。但这也意味着 PM 的角色转变最大——从「信息收集者」变为「决策制定者」。

### 不可做的边界

```
✗ Agent 不能替代人的地方：
├── 人事判断：某个任务延期是因为能力不够还是任务确实太复杂
├── 冲突调解：两个团队对排期有争议，需要人协商和建立共识
├── 向上管理：向管理层汇报时，什么语气、什么时机、强调什么
├── 团队激励：感知团队士气、做团建，这些需要人的同理心
├── 紧急事件决策：线上事故时的资源调配决策
└── 战略排期：优先级冲突时的最终拍板

✗ Agent 使用限制：
├── 会议录音需要参与者知情同意
├── 进度数据绝对不能对外泄露（涉及产品路线图等机密信息）
├── Agent 生成的报告在发送前必须人审核（避免数据错误导致的误判）
├── 不要用 Agent 替代和团队成员的直接沟通（进度问当事人好过只靠工具）
└── Jira/TAPD API 的写权限不要给 Agent（避免误操作批量改状态）
```

### 常见陷阱

1. **报告替换了沟通**：有了自动生成的日报，PM 可能减少和团队成员的一对一沟通。但工具展示的「进度」和真实情况总有差距。
2. **信息过载**：Agent 可以监控一切 → PM 收到一大堆告警 → 反而无法聚焦真正重要的问题。需要设置合理的告警阈值。
3. **机械的风险评估**：Agent 判断「有风险」基于规则（deadline - 进度 < 阈值），但不会考虑「这个开发比较强，三天搞定」这类软信息。
4. **会议纪要的隐私问题**：不是所有会议都适合录音让 Agent 处理（如绩效面谈、裁员讨论）。
5. **数据边界**：Jira 状态不等于真实进展——Agent 能基于 Jira 出报告，但不能替代人去验证 Jira 信息是否准确。

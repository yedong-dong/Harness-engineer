# 测试工程师 × Agent 深度应用指南

> 状态：**已落地验证** | 本项目 prd-testcase-xmind Skill 是完整参考实现

---

## 1. 角色画像

### 核心职责

测试工程师负责保障产品质量，核心工作包括：理解需求、设计测试用例、执行测试、定位 Bug、输出测试报告、维护自动化测试体系。

### 典型的一天

```
09:30  打开 TAPD/Jira，看新分配的需求文档和 Bug 单
10:00  开始读 PRD，画思维导图，拆解测试点
11:00  就需求模糊点和产品经理对齐
14:00  写测试用例（Excel/XMind）
16:00  执行用例、提 Bug、跟踪回归
18:00  写测试日报/周报
```

### 关键 KPI

- 用例覆盖率（需求覆盖 / 代码覆盖）
- 线上 Bug 漏出率
- 用例执行效率（条/天）
- Bug 发现阶段分布（提测 vs 线上）

### 与上下游的依赖

```
产品经理 ──PRD──→ 测试工程师 ──Bug──→ 开发工程师
                    │
                    ├──用例──→ 测试平台/用例库
                    └──报告──→ 项目经理/Leader
```

## 2. 核心痛点深度分析

### P0-1：用例设计占 50% 时间，是最大瓶颈

- **现状**：一个中等复杂度的需求（如"女性权益聚合"），从读 PRD 到写完测试脑图，熟练的测试工程师需要 4-6 小时。这期间的工作是：逐段拆解需求 → 识别功能点 → 按正常/边界/异常/状态流转/数据一致性五个维度展开 → 逐条写前置条件、步骤、预期结果。
- **耗时估算**：每周约 15-20 小时（占 40%-50% 工作量）
- **痛苦根源**：
  - 需求文档质量参差不齐：有的太简略需要猜，有的太冗长需要提炼
  - 五维度展开是纯脑力劳动，但规则非常明确——"充值金额边界值测试"无论是谁测、测哪个业务，模式完全一样
  - 思维导图工具操作本身也耗时（拖拽节点、调整格式）
- **Agent 可替代性分析**：
  - 读 PRD 并提取功能点 → 规则明确，量大 ✓
  - 按五维度展开用例 → 模式固定，可模板化 ✓
  - 写前置条件/步骤/预期 → 有清晰的规范可遵循 ✓
  - 需要产品/业务理解 → 人校对 + 补充边界 ✗（人类把关）

结论：Agent 可以完成 80% 的用例设计初稿工作，人只用做审核和补充。

### P0-2：需求和接口频繁变更，用例更新跟不上

- **现状**：开发提测前一天，产品在群里说"这个字段改成非必填了"或"这个流程加了一个分支"。测试工程师需要手工排查受影响范围，手动修改已有用例。
- **耗时估算**：每次变更 1-3 小时，频繁时每周 6-10 小时
- **痛苦根源**：手工排查影响范围极易遗漏——"改了充值金额的下限，是否影响到退款逻辑？"这类跨模块影响极难脑补。
- **Agent 可替代性分析**：
  - diff 需求变更 → Agent 可直接对比新旧文档 ✓
  - 自动识别受影响用例 → Agent 可反向追溯（需求点 → 用例映射）✓
  - 生成需要新增/修改的用例 → 可以自动化生成 ✓

### P1-1：回归测试手工执行，效率低且不稳定

- **现状**：每次发版前手工执行回归用例，每次约 50-100 条，重复操作但不可跳过。
- **耗时估算**：每次发版 4-8 小时
- **痛苦根源**：回归用例执行没有智力含量但必须人点——自动化脚本开发成本高，且 App 端 UI 变更频繁导致脚本维护成本更高。
- **Agent 可替代性分析**：
  - Agent 不能直接操作手机（UI 自动化需要其他工具）
  - 但 Agent 可以根据回归用例列表生成自动化脚本初稿
  - 可以自动生成接口回归的 curl/脚本（服务端回归）

### P1-2：Bug 根因分析依赖经验和运气

- **现状**：拿到一个 Bug 单（如"用户 138xxx 充值 100 元未到账"），需要查多个系统的日志、数据库记录，手工关联时间线。
- **耗时估算**：简单 Bug 10-30 分钟，复杂 Bug 2-4 小时
- **痛苦根源**：日志分散在多个系统，查日志本身不困难，但"在哪个系统查什么字段"依赖经验。
- **Agent 可替代性分析**：
  - 将 Bug 描述 + 日志 + DB 记录喂给 Agent → 自动关联时间线 ✓
  - 但需要给 Agent 只读的日志和 DB 访问权限

### P2：测试报告编写占发布日时间

- **现状**：发版日晚间需要汇总用例执行情况、Bug 统计、风险评估，写一份测试报告。
- **耗时估算**：每次 30-60 分钟
- **Agent 可替代性分析**：完全可由 Agent 从用例执行数据和 Bug 系统中自动生成。

```

                                    ↑
```

## 4. 落地路径

### Phase 1：PRD → 用例自动生成（1 周，已跑通）

**做什么**：
1. 把 PRD + 技术文档 + 接口文档喂给 Agent
2. Agent 按五维度（正常/边界/异常/状态流转/数据一致性）生成用例
3. 人工审核 + 补充后导入平台

**用什么工具**：
- Claude Code + Skill 体系
- prd-testcase-xmind Skill（本仓库已实现）
- .mcp.json 连接用例管理平台

**预期收益**：
- 用例设计时间：6h → 1.5h（节省 75%）
- 覆盖率：人工 60-70% → Agent + 人补充 85-95%

**实际落地参照**：
- 本项目 `PRD/Achat3.22-女性权益聚合/` —— 完整案例
- 本项目 `PRD/Achat-亲密度等级重构/` —— 验证案例
- Skill 代码：`.claude/skills/prd-testcase-xmind/`

### Phase 2：变更影响分析 + 自动回写（1 个月，构建中）

**做什么**：
1. 需求/接口变更时，Agent 自动 diff 新旧文档
2. 识别受影响的功能点 → 映射到已有用例
3. 生成需要新增/修改的用例列表
4. 一键更新用例库

**关键挑战**：
- 需要建立「功能点 → 用例」的映射关系（已在 coverage_manifest.json 中实现）
- 变更描述往往是非结构化的群消息，需要先结构化

**预期收益**：
- 变更响应时间：3h → 30min

### Phase 3：Bug 根因分析 + 接口自动化生成（持续优化）

**做什么**：
1. 接入只读日志 + DB 权限，Agent 辅助 Bug 排查
2. 从用例 JSON 自动生成接口自动化脚本（Python/Go）
3. 接入 CI 流水线，Agent 读取测试结果并生成报告

**预期收益**：
- Bug 排查：复杂 Bug 2h → 30min
- 测试报告：60min → 5min
- 回归效率：提升 3-5x

## 5. Prompt 模板

### 模板 1：PRD → 测试点拆解

```
你是一个互联网测试工程师。请阅读以下 PRD 文档，按五个维度拆解测试点：

【五维度规范】
- 正常路径：核心功能的主流程
- 边界值：数值上下限、字符串长度、时间范围
- 异常路径：网络异常、超时、并发、权限不足
- 状态流转：各状态的触发条件和合法转换
- 数据一致性：多端/多表/缓存数据的一致性校验

【输出格式】
每个测试点：{维度} | {功能模块} | {测试场景} | {预期结果}

【PRD 文档】
{粘贴 PRD 内容}
```

### 模板 2：接口文档 → 服务端用例

```
你是一个服务端测试工程师。请根据以下接口文档生成服务端测试用例：

【覆盖要求】
- 每个接口：正常参数 → 参数必填校验 → 参数边界值 → 异常请求方式
- 多接口联动：数据流转一致性
- 并发：幂等性、并发安全性

【接口文档】
{粘贴接口文档}
```

### 模板 3：Bug 日志辅助分析

```
你是一个测试工程师。以下是一个 Bug 的相关信息，请帮我分析可能的根因：

【Bug 描述】
{Bug 标题 + 复现步骤}

【用户操作时间线】
{用户行为日志}

【服务端日志】
{服务端日志片段}

请给出：
1. 最可能的根因（Top 3，按可能性排序）
2. 需要补充查看的日志/数据
3. 建议的验证方案
```

### 模板 4：生成接口自动化脚本

```
你是一个测试开发工程师。请根据以下测试用例 JSON，生成 Python 接口自动化脚本：

【用例 JSON】
{cases.json 内容}

【技术要求】
- 使用 requests 库
- 断言包含 HTTP 状态码 + 业务 code + 关键字段
- 每个用例独立函数，可单独运行
```

### 模板 5：测试报告自动生成

```
根据以下数据生成一份发版测试报告：

【用例执行】
- 总用例数：{N}
- 通过：{N1}，失败：{N2}，阻塞：{N3}
- 执行覆盖率：{百分比}

【Bug 统计】
- 本次新增 Bug：{列表}
- 未修复遗留 Bug：{列表}

【变更范围】
{本次变更的功能列表}

输出格式：Markdown，包含执行摘要、风险等级（红/黄/绿）、遗留问题列表。
```

### 模板 6：用例评审辅助

```
你是一个资深测试专家。请评审以下测试用例的质量：

【评审维度】
- 覆盖完整性：是否遗漏关键场景
- 步骤清晰度：其他人能否直接执行
- 预期结果可验证性：是否有明确的可观察结果

【用例列表】
{粘贴用例}

请给出：评分（1-10）+ Top 5 问题 + Top 3 补充建议。
```

```
【旧版 PRD】

{新版内容}
```

## 6. 收益预估 & 风险边界

### 量化收益

| 环节 | 纯人工 | Agent + 人 | 节省比例 |
|------|--------|-----------|---------|
| 用例设计（单需求） | 4-6h | 1-1.5h | 70-75% |
| 需求变更响应 | 2-3h | 0.5h | 75-85% |
| 测试报告 | 1h | 5min | 90% |
| Bug 根因定位（复杂） | 2-4h | 0.5h | 75-85% |
| 接口脚本编写 | 2h/接口 | 0.3h/接口 | 85% |
| **每周总计** | **~35h** | **~12h** | **~65%** |

### 不可做的边界

```
✗ Agent 不能替代人的地方：
├── 业务判断：某个行为是否属于 Bug 还是需求理解偏差
├── 体验评估：UI 交互是否「好用」，不是功能是否「正确」
├── 风险决策：遗留 Bug 是否可接受发版（人决策，Agent 只提供数据）
├── 跨部门沟通：和产品/开发就争议点达成共识
└── 探索性测试：不按固定路径的随机测试（Agent 擅长结构化，不擅长发散）

✗ 永远不能给 Agent 的权限：
├── 数据库写操作（INSERT/UPDATE/DELETE）
├── 生产环境命令执行
└── 未经人工确认的用例/脚本直接上线
```

### 常见陷阱

1. **幻觉风险**：Agent 可能生成看起来合理的用例，但实际上该功能不存在或逻辑相反。必须逐条人工确认。
2. **过度依赖**：Agent 生成的用例往往偏「标准」，容易遗漏业务特有的边界场景。人工审核必须针对业务特异性补充。
3. **上下文衰减**：复杂 PRD 超过 Agent 上下文窗口时，长尾部分可能被忽略。需要合理拆分子模块。
4. **维护成本假象**：以为引入 Agent 就不需要维护——实际上 Prompt 模板、Skill 配置本身需要持续迭代。
5. **质量门控缺失**：直接用 Agent 输出不做质量检查是最大的风险。必须引入独立的 Evaluator 评估环节（本项目已实现）。

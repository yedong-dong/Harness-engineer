# RAG 详解：让 AI 能「查资料」再回答

## 1. 这是什么

RAG（Retrieval-Augmented Generation，检索增强生成）解决 LLM 的一个根本缺陷：**AI 只知道训练数据里的东西，不知道你公司的内部知识**。

```
没有 RAG：
  用户：「我们公司的充值接口超时时间是多少？」
  AI：「抱歉，我不知道你们公司的具体配置...」

有了 RAG：
  用户：「我们公司的充值接口超时时间是多少？」
  AI（先查内部文档 → 找到技术方案 → 基于文档回答）：「根据《支付接口技术方案v2.3》，
  充值接口超时时间为 30 秒，超时后触发轮询重试机制。」
```

## 2. 核心原理

### 2.1 RAG 的两阶段流程

```
┌─────────────────────────────────────────────────────────────┐
│                      RAG 工作流程                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────────────────┐    ┌──────────────────────┐       │
│  │   阶段1：检索（Retrieval）│    │  阶段2：生成（Generation）│       │
│  │                      │    │                      │       │
│  │  用户问题              │    │  原始问题              │       │
│  │    ↓                 │    │    ↓                 │       │
│  │  向量化（Embedding）   │    │  + 检索到的文档片段     │       │
│  │    ↓                 │    │    ↓                 │       │
│  │  在知识库中搜索        │    │  组装成完整 Prompt     │       │
│  │    ↓                 │    │    ↓                 │       │
│  │  返回最相关的 Top K    │    │  LLM 基于文档生成回答   │       │
│  │                      │    │                      │       │
│  └──────────────────────┘    └──────────────────────┘       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 知识库的构建（离线阶段）

在使用 RAG 之前，需要先把文档「喂」进去：

```
原始文档（PRD、技术方案、接口文档、历史Bug记录...）
    ↓
① 文档分块（Chunking）
  把长文档切成小段。为什么？→ 向量搜索在短文本上更准
  策略：
  - 固定大小切（如 500 字一块，重叠 50 字）
  - 或按段落/标题语义切
    ↓
② 向量化（Embedding）
  把每段文字转成向量（一组数字），语义相近的文字向量也相近
  例：「充值失败」和「支付异常」的向量距离很近
  工具：OpenAI text-embedding-3-small / 阿里云 embedding / 开源 bge-large
    ↓
③ 存入向量数据库
  向量数据库专门做「找最相似的向量」这件事
  工具：Chroma（轻量）/ Pinecone（云）/ Milvus（开源）/ pgvector（PostgreSQL插件）
    ↓
④（可选）元数据标注
  每块文档附加标签：来源文件、日期、作者、业务线
  用途：搜索时可以加过滤条件
```

### 2.3 检索阶段（在线阶段）

```
用户问题：「充值接口超时怎么处理？」
    ↓
① 将问题向量化（用同一个 Embedding 模型）
    ↓
② 在向量数据库中搜索最相似的 Top K 个文档块
   「充值接口超时」的向量 vs 知识库中所有块的向量 → 找最近的 5 个
    ↓
③（可选）重排序（Re-ranking）
  向量相似 ≠ 语义相关，用一个更强的模型重新排序
    ↓
④ 返回 Top K 个文档块的原文
```

### 2.4 生成阶段

```
将检索到的文档 + 用户问题组装成 Prompt：

"""
你是一个技术支持助手。请根据以下资料回答用户问题。

【参考资料】
{检索到的文档块1}
---
{检索到的文档块2}
---
{检索到的文档块3}

【回答规则】
- 只使用参考资料中的信息
- 如果资料中没有答案，明确告知用户「根据现有文档无法确定，建议查阅XXX」
- 回答中引用具体的文档名称

【用户问题】
{用户问题}
"""
    ↓
LLM 基于这个 Prompt 生成回答
```

## 3. 两种 RAG 模式

### 3.1 传统两阶段 RAG

```
用户问 → 检索 → LLM回答
```

优点：简单、响应快
缺点：只检索一次，如果第一次没找对，答案就歪了

### 3.2 Agentic RAG（Agent 驱动的 RAG）

```
用户问 → Agent 决策：
    ├── 需要检索 → 调用 search 工具 → 拿到结果 → 判断够不够
    │       ├── 够了 → 回答
    │       └── 不够 → 换关键词再搜 → 再判断
    ├── 不需要检索 → 直接回答
    └── 需要多轮检索 → search("充值接口") → search("超时处理") → 交叉对比
```

**Agentic RAG = RAG + Tool Calling + 条件循环**

这和你的 Generator/Evaluator 循环是一个道理——Agent 有判断能力后，不再是固定的「搜一次→答一次」，而是可以动态调整检索策略。

## 4. RAG vs 长上下文

一个常见的疑问：现在 Claude/Gemini 支持 100K+ 上下文了，直接把所有文档丢进去不就行了？为什么还要 RAG？

| 维度 | RAG | 直接丢文档 |
|------|-----|-----------|
| 文档量 | 理论上无限（只要向量库能存） | 受上下文窗口限制 |
| 成本 | 每次只把最相关的片段送进 LLM | 全文送，Token 消耗巨大 |
| 精度 | 检索可能漏掉相关内容 | 只要在上下文内，不会漏 |
| 延迟 | 检索+生成 | 只生成（但上下文长时生成也会变慢） |
| 适用场景 | 文档量大、更新频繁 | 文档量小、需要全文理解 |

**实际最佳实践**：两者结合。用 RAG 检索最相关的内容，再用 LLM 在少量精炼的上下文中做深度分析。

## 5. 与你已有知识的连接

### 5.1 你的「PRD 分析」本质上是一种简单的 RAG

当你把 PRD + 技术文档喂给 Agent 时：

```
PRD 全文 ──→ Agent 上下文 ──→ Agent 基于文档生成用例
```

这是一个「全文在上下文内」的模式，不是严格的 RAG。但如果未来你的文档库有 100 份 PRD、500 份技术方案，就不能全塞进上下文了——那时候就需要 RAG：只检索和当前需求相关的文档。

### 5.2 RAG 在你的 Skill 体系中的位置

```
当前 Skill（无 RAG）：
  用户提供 PRD → Agent 分析 → 生成用例
  前提：PRD 是明确给出的，文档量可控

加入 RAG 后：
  用户说「我要测充值功能」→ Agent 去知识库检索相关文档
  → 找到：充值PRD v2.3、支付接口方案、历史充值Bug列表
  → 基于这些文档生成用例（覆盖了历史Bug场景）
```

### 5.3 你的 memory 文件系统 = 轻量 RAG

你的 `memory/` 目录本质上是手工维护的「知识库」——存了用户偏好、项目知识、反馈记录。RAG 是把这件事自动化 + 规模化：不用手工整理，AI 自动检索相关记忆。

## 6. 动手实现：最小 RAG Demo

```python
# 依赖：pip install chromadb sentence-transformers

import chromadb
from sentence_transformers import SentenceTransformer

# ===== 离线阶段：构建知识库 =====

# ① 加载 Embedding 模型
embedder = SentenceTransformer("all-MiniLM-L6-v2")

# ② 创建向量数据库
chroma_client = chromadb.Client()
collection = chroma_client.create_collection(name="test_docs")

# ③ 文档分块 + 入库
documents = [
    "充值接口POST /api/recharge，超时时间30秒，超时后每5秒轮询一次，最多轮询3次。",
    "充值金额限制：单笔最低1元，最高100000元，单日累计上限500000元。",
    "充值失败常见原因：1.支付渠道超时 2.用户余额不足 3.风控拦截 4.参数校验失败",
    "用户等级与充值优惠：VIP1 无优惠，VIP2 98折，VIP3 95折，VIP4 9折。",
    "退款流程：用户申请→客服审核（1工作日）→财务打款（1-3工作日）→到账通知。",
]

# 向量化 + 存入
embeddings = embedder.encode(documents)
collection.add(
    documents=documents,
    embeddings=embeddings,
    ids=[f"doc_{i}" for i in range(len(documents))]
)

# ===== 在线阶段：检索 + 生成 =====

def rag_query(question: str, top_k: int = 3):
    # ① 问题向量化
    question_embedding = embedder.encode([question])

    # ② 检索最相关的文档
    results = collection.query(
        query_embeddings=question_embedding,
        n_results=top_k
    )

    # ③ 组装 Prompt
    retrieved_docs = results["documents"][0]
    context = "\n---\n".join(retrieved_docs)

    prompt = f"""请根据以下参考资料回答用户问题。如果资料中没有答案，请如实告知。

【参考资料】
{context}

【用户问题】
{question}

【回答要求】
- 必须引用具体的数据和规则
- 如果涉及多个资料，说明各自适用的场景"""

    # ④ 调用 LLM（这里省略，用你已有的 Anthropic SDK）
    # response = llm.invoke(prompt)
    return prompt  # 展示组装的 Prompt 结构

# 测试
print(rag_query("充值失败了可能是什么原因？"))
print("=" * 60)
print(rag_query("VIP3用户充值有什么优惠？"))
```

运行这个 Demo，你会发现：
- 第一个问题最匹配文档3（充值失败原因），文档1（超时即失败的一种）也会被拉进来
- 第二个问题最匹配文档4（VIP规则）

### 答案 2

LLM 回答的两个问题：

1. **幻觉（Hallucination）**：文档中没有任何关于 VIP2 的信息，但 LLM 编造了「和 VIP3 相似，享受 95 折」。正确做法是说「根据现有文档，未找到 VIP2 用户的充值优惠信息，建议查阅用户等级完整规则文档。」

2. **文档外推不标注**：即使 LLM 推测 VIP2 和 VIP3 的优惠可能相似（合理推测），也应该明确标注「文档中未直接提及 VIP2，以下是基于 VIP3/VIP4 规则的推测：...」

**根因**：Prompt 中没有强制约束「只使用资料中的信息」。应该加：「如果资料中没有相关信息，必须明确说『资料中未找到』，禁止猜测或类比。」

### 答案 4

```python
# 三个评测维度

# 维度1：检索质量（检索到的东西对不对）
eval_dimension_1 = {
    "name": "检索命中率（Recall@K）",
    "method": """
    准备 50 个问题，人工标注每个问题应该匹配哪些文档块（Ground Truth）。
    RAG 检索 Top K 个结果，计算：
    Recall@K = 命中的正确文档数 / 所有应返回的正确文档数

    例：问题「充值超时怎么处理」应返回文档块 [A, B, C]。
    RAG 返回 Top 5 中有 [A, B, D, E, F] → Recall@5 = 2/3 = 0.67
    """,
    "target": "> 0.85"
}

# 维度2：答案质量（基于检索到的文档，答案对不对）
eval_dimension_2 = {
    "name": "答案忠实度（Faithfulness）",
    "method": """
    用人或另一个 LLM 评估：答案中的每句话是否都能在检索到的文档中找到依据。
    Faithfulness = 有依据的句子数 / 总句子数

    例：答案 5 句话，其中 4 句能在文档中找到原文支持，1 句是 LLM 编的 → 0.8
    """,
    "target": "> 0.95（这个指标应该很高——AI 不应该编）"
}

# 维度3：答案完整性（该有的答案信息都有了吗）
eval_dimension_3 = {
    "name": "答案相关性（Answer Relevance）",
    "method": """
    人评估：答案是否完整回答了用户的问题。
    评分 1-5：
    1 — 完全不相关
    3 — 部分相关，缺了重要信息
    5 — 完整、准确地回答了问题
    """,
    "target": "平均 > 4.0"
}
```

一个完整的 RAG 评测应该同时看检索质量（检索对了吗）和生成质量（答案对吗）——因为两段都可能出问题。

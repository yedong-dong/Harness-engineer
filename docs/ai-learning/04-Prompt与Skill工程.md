# Prompt 与 Skill 工程详解

> 本章与你已有的知识高度重合——你的 prd-testcase-xmind 就是 Prompt + Skill 工程的完整实践。本章的目标是帮你把 **经验** 系统化为 **方法论**，让这些原则可以迁移到任意岗位。

## 1. Prompt 工程

### 1.1 Prompt 是什么

Prompt 是你给 AI 的指令。但「指令」这个词容易让人低估它的复杂性——Prompt 本质上是一种 **对 AI 行为的编程**，只是编程语言是自然语言。

```
传统编程：  代码 → 编译器 → 确定性的二进制行为
Prompt 编程：自然语言 → LLM → 概率性的文本/行为输出
```

Prompt 工程的核心挑战是：**如何用自然语言稳定地控制一个概率系统。**

### 1.2 Prompt 的四层结构

一个完整的 Prompt 包含四个层次：

```
┌──────────────────────────────────────┐
│ ④ 输出格式约束（Output Format）        │  ← 结构化、可解析
│    JSON schema / Markdown 模板 / 示例  │
├──────────────────────────────────────┤
│ ③ 任务拆解（Task Decomposition）       │  ← 复杂任务分步
│    步骤1 → 步骤2 → 步骤3              │
├──────────────────────────────────────┤
│ ② 上下文注入（Context）               │  ← 背景知识、参考材料
│    项目规则 / 术语表 / 历史案例         │
├──────────────────────────────────────┤
│ ① 角色与目标（Role & Goal）           │  ← 最基础层
│    "你是一个测试工程师..."             │
└──────────────────────────────────────┘
```

**每一层用一个你实际写过的 Prompt 来对照**：

```
你是一个互联网测试工程师。               ← ① 角色
请阅读以下 PRD 文档，这个项目是...        ← ② 上下文
按以下五个维度拆解：
1. 正常路径 2. 边界值 3. 异常路径         ← ③ 任务拆解
4. 状态流转 5. 数据一致性
输出格式：每条用例包含标题/前置条件/...    ← ④ 输出格式
```

### 1.3 Prompt 稳定性的五个原则

#### 原则 1：正向指令优于反向指令

```
❌ 「不要省略边界条件测试，不要只写正常路径」
   → AI 需要先理解"不要"，再推理"那我要什么"，两步跳转容易出错

✅ 「必须覆盖 5 个维度：正常、边界、异常、状态流转、数据一致性」
   → 直接告诉 AI 做什么，一步到位
```

#### 原则 2：约束要具体，不能笼统

```
❌ 「输出要详细」
✅ 「每条用例至少包含 3 个步骤，预期结果必须包含可观察的具体现象」
```

#### 原则 3：先给规则，再给例外

```
✅ 「默认所有数值字段都要测边界值。例外：枚举类型字段不需要边界值测试。」
```

#### 原则 4：利用示例（Few-shot）建立模式

```
❌ 只描述规则
✅ 描述规则 + 2-3 个完整示例

示例 1：
标题：充值金额为 0 时提示错误
前置：用户已登录，余额充足
步骤：1.进入充值页 2.输入金额0 3.点击确认
预期：提示"充值金额需大于0"，不跳转支付页
```

#### 原则 5：复杂任务拆解为子任务

```
❌ 「根据这份 PRD 生成完整的测试用例脑图和覆盖率报告」
   → 任务太大，AI 可能在某个环节偷懒

✅ 拆为多个 Prompt/Agent 调用：
   步骤1：提取功能点
   步骤2：为每个功能点生成用例（可并行）
   步骤3：合并 + 去重
   步骤4：生成覆盖率报告
   步骤5：导出 XMind
```

你的 Fan-out Fan-in 模式本质上就是原则 5 的工程化实现。

### 1.4 Prompt 评估与迭代

```
写 Prompt → 跑 10 个 case → 找失败 pattern → 改 Prompt → 再跑 → 直到稳定

关键动作：
  不是 "Prompt 好不好" 的主观判断
  而是 "在哪些 case 上失败" 的客观追踪
```

## 2. Skill 工程

### 2.1 Skill vs Prompt 的本质区别

```
Prompt：
  一段文字，每次用的时候粘贴
  问题是：每次都要手动提供上下文 → 低效 → 容易漏

Skill：
  一个可被 Agent 按需加载的「能力包」
  包含：任务描述 + 参考知识 + 工具入口 + 流程定义 + 模板/脚本
  问题是：设计成本高 → 适合沉淀，不适合一次性的任务
```

形象比喻：

```
Prompt = 口头交代：「帮我查一下上周的订单数据」
Skill  = 培训手册 + 工具包 + 权限卡：「这个人会查数据，给他看培训手册，
         他就能用这些工具独立查各种数据了」
```

### 2.2 Skill 的四个组成部分

以你的 prd-testcase-xmind 为例：

```
prd-testcase-xmind/
├── SKILL.md              ← 核心：任务描述 + 流程 + 何时加载
├── references/           ← 参考知识
│   ├── agent-prompt.md        → 各 SubAgent 的 Prompt 模板
│   ├── evaluator-prompt.md    → 评估器的 Prompt 模板
│   ├── review-rules.md        → 审核规则
│   ├── cases-json-schema.md   → 输出格式 schema
│   └── xmind-output-schema.md → XMind 格式 schema
├── scripts/              ← 可执行脚本
│   ├── export_xmind.py        → 导出 XMind 文件
│   └── validate_coverage.py   → 验证覆盖率
└── templates/            ← 模板文件
    └── template.xmind         → XMind 模板
```

各部分的职责：

| 组件 | 职责 | 加载时机 |
|------|------|---------|
| SKILL.md | 定义这技能做什么、怎么触发 | 始终在 Skill 目录中，按需被 Agent 发现 |
| references/ | 详细的知识、规范、Prompt 模板 | Agent 加载 Skill 时按需读取 |
| scripts/ | 确定性操作（格式转换、校验） | 明确需要时执行 |
| templates/ | 静态资源文件 | 输出阶段引用 |

### 2.3 SKILL.md 的写法

```markdown
# Skill 名称（简短、描述性强）

## 触发条件
- 用户提到"PRD"、"测试用例"、"XMind"、"需求转测试"时触发
- 触发条件要具体但不过窄——让 Agent 在该触发时触发，不该触发时不触发

## 任务描述
一句话：将 PRD 文字直接转换为 XMind 测试用例脑图。

## 工作流程
流程：阶段1 → 阶段2 → 阶段3 → 阶段4
每阶段：谁做什么、输出什么、交接条件

## 角色分配
- 主 Agent：调度 + 合并
- SubAgent：生成
- Evaluator：评估
每角色的 Prompt 模板在 references/ 中

## 输出规范
- XMind：符合 template.xmind 格式
- cases.json：符合 cases-json-schema.md schema
- 覆盖率报告：包含维度覆盖率统计
```

### 2.4 Skill 的发现机制

Agent 不是一开始就把所有 Skill 的内容都加载到上下文（那样会爆掉上下文窗口）。而是：

```
Agent 初始化
    ↓
    扫描所有 Skill 目录
    ↓
    只读取每个 Skill 的 SKILL.md（很小，几百字）
    ↓
    根据用户输入，匹配触发条件
    ↓
    匹配到的 Skill → 加载其 references/scripts/templates
    未匹配的 Skill → 不加载，节省上下文
```

**所以 SKILL.md 的质量直接决定 Skill 是否被正确触发。**

### 2.5 Skill 工程的进阶：评测闭环

你已经在做的 Generator/Evaluator 分离，本质上是把「Prompt/Skill 好不好」从主观判断变为客观追踪：

```
Skill 执行
    ↓
Evaluator 独立评分
    ↓
┌── 评分 < 阈值 ──→ 给出 regenerate_hint ──→ 回修 ──→ 再评
│
└── 评分 ≥ 阈值 ──→ 通过
    ↓
人工审核时发现的问题
    ↓
反哺 regenerate_hint → 更新到 references/review-rules.md
    ↓
下次 Evaluator 自动检查这个点
```

**每一轮 Skill 的执行都在改进 Skill 本身。**

## 3. 你已经会的 vs 可以补的

### 你已经掌握得很好

- Prompt 的四层结构：你的用例生成 Prompt 是标准范例
- Skill 组织：prd-testcase-xmind 的目录结构是正确实践
- 评估闭环：Generator/Evaluator 分离是最佳实践
- 复杂任务拆解：Fan-out/Fan-in 解决并行生成

### 可以补的

1. **Prompt 的版本管理**：每次修改 Prompt，记录「改了什么 + 为什么 + 在哪些 case 上改善了」。这让你可以回溯 Prompt 的演化历史。

2. **Skill 的可迁移性**：把「测试工程师的 Skill」中的通用模式（调度+并行生成+独立评估+回修）抽象出来，应用到产品经理写 PRD、运营写内容等场景——你已经在做这一步了（AIdoc 下的岗位文档）。

3. **Prompt 的边界测试**：不只测「正常 PRD 生成正常用例」，还要测：
   - 极端短的 PRD（只有一段话）
   - 极端长的 PRD（超过上下文窗口）
   - 包含矛盾的 PRD（2.1 节说 A，3.2 节说 not A）
   - 纯图没有文字的 PRD

4. **Skill 之间的组合**：当前你的 Skill 是独立的。未来可以让多个 Skill 组合——例如「先让 PRD 评审 Skill 审查 PRD → 再去生成用例 → 再用导入 Skill 上传」。

## 5. 答案

### 答案 1

三个隐藏假设：

1. **「生成测试用例」没有指定覆盖深度**
   - AI 可能理解为「每个功能点生成 1-2 条用例」
   - 实际需要：每个功能点按五个维度每条至少 1 条，复杂逻辑每条至少 3 条
   - 修正：加「每个功能点必须覆盖：正常路径≥1条、边界值≥2条、异常路径≥2条」

2. **「步骤」的粒度不明确**
   - AI 可能写「1.操作 2.查看结果」
   - 实际需要：每一步是一个具体动作，另一人可以直接执行
   - 修正：加写示例

3. **「预期结果」缺少可验证性约束**
   - AI 可能写「系统正常工作」
   - 实际需要：具体到可观察的现象（页面显示什么、接口返回什么 code）
   - 修正：加「预期结果必须包含具体的、可观察的现象」

### 答案 2

问题：「当用户需要帮助的时候」——太宽泛，几乎所有对话都会触发，导致 Agent 在不需要时也加载此 Skill，浪费上下文。

改写：
```
触发条件：触发本 Skill 的场景——
- 用户提供了 PRD、需求文档、或产品方案文字描述
- 用户提到「生成测试用例」、「PRD转用例」、「XMind」、「测试脑图」、「需求转测试」
- 用户说「帮我分析这个需求要测什么」

不触发的场景：
- 用户只是在聊天中提到「之前那个 Skill 很好用」（没有新任务）
- 用户讨论的是接口测试、UI自动化、性能测试（本 Skill 聚焦功能测试）
```

### 答案 3

| 测试 Case | 输入 | 期望行为 | 可能失败模式 |
|-----------|------|---------|------------|
| 1. 超短 PRD | 一句话：「用户可以通过支付宝充值」 | 至少生成充值正常流程 + 金额边界 + 支付异常 | AI 可能只生成 1-2 条，漏掉边界和异常 |
| 2. 超长 PRD | 50KB+ 的完整产品方案 | 提取所有功能点，不遗漏 | AI 可能丢失长尾功能点（上下文窗口尾部） |
| 3. 矛盾 PRD | 第2章说「充值上限100000」，第5章说「充值上限50000」 | 标注矛盾并请求澄清，而不是随便选一个 | AI 可能随意选一个值，不一致 |
| 4. 纯表格 PRD | PRD 全是表格，无叙述文字 | 正确解析表格中的数据定义和规则 | AI 可能忽略表格中的约束条件 |
| 5. 无技术背景 PRD | 用口语写的需求，如「点一下就能付钱的那种」 | 翻译为规范的测试术语 | AI 可能照搬口语描述，专业度不够 |

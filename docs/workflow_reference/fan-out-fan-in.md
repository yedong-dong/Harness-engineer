# Fan-out / Fan-in：SubAgent 并行派发架构

```
                           ┌─ SubAgent-1（模块A·8条）──┐
                           ├─ SubAgent-2（模块B·11条）─┤
  主Agent（拆解 + 派发）───┼─ SubAgent-3（模块C1·9条）─┼── 合并去重 ──┬── Evaluator ── 导出
                           ├─ SubAgent-4（模块C2·7条）─┤              │
                           └─ SubAgent-5（模块D·9条）──┘              │
                                                                     │
                              ★ 同一条消息并行派发                     │
                              ★ 互不依赖，各自写 /tmp/cases_*.json     └── 不通过 → 回修（最多3轮）
```

## 关键特征

```
  Fan-out（发散）          Fan-in（汇合）           质量门（阻断）
  ════════════           ════════════           ══════════════
  1 条消息 → N 个 Agent    N 组输出 → 1 份 cases   1 个 Evaluator
  并行执行，互不阻塞       自动去重 + 字段校验      独立上下文，盲评
```

## 拆分规则（负载均衡）

```
  按模块树一级分组
        │
        ├─ 单模块 ≤ 12 条 ──→ 独立 SubAgent
        ├─ 单模块 > 12 条 ──→ 强制再拆
        └─ 单 Agent 总量 > 20 ──→ 强制再拆（即使各子模块都不超 12）

  ★ 拆完后核对：各 Agent 预估 case 数应尽量接近
  ★ 避免出现一个 32、一个 8 的情况
```

## 数据流

```
  主 Agent                      SubAgent                       主 Agent
  ────────                      ────────                       ────────
  派发时传入：                   输出到：                        收集后：
  · PRD 模块片段                /tmp/cases_{模块代号}.json       · 合并 → 去重
  · 技术摘要（分级过滤）                                        · 字段校验
  · 交叉校验差异表                                             · 写 cases.json
  · 约束限制                                                   · 交 Evaluator
  · 用户确认决策
```

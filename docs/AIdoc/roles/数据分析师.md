# 数据分析师 × Agent 深度应用指南

> 状态：待验证 | 基于三步分析法推理，SQL 生成已有大量成熟方案参考

---

## 1. 角色画像

### 核心职责

数据分析师负责从数据中提取业务洞察。核心工作：理解业务问题、取数与清洗、做分析（归因/趋势/对比）、输出分析报告、搭建看板。

### 典型的一天

```
09:30  看邮件/群消息：今天有几个临时取数需求
10:00  写 SQL，跑数据（需求A：上周的留存率为什么跌了）
11:00  清洗数据、做透视表、画图
11:30  需求A结果发给业务方，附分析说明
14:00  周报时间：自动化脚本拉数据 → 更新 Excel/看板
15:00  需求B：新功能上线的 AB 实验分析
16:00  深入分析：发现留存跌可能和某个渠道的用户质量有关
17:30  写分析报告（PPT/文档）
18:30  业务方追问：「这个数据能再加一个维度吗？」→重新跑 SQL
```

### 关键 KPI

- 取数需求响应时效
- 分析报告产出量
- 分析建议被采纳次数
- 数据看板覆盖率

### 与上下游的依赖

```
业务方（产品/运营/管理层）──需求──→ 数据分析师 ──报告──→ 业务方
  数据仓库/平台                       │
  埋点/日志                           ├──SQL──→ 数据库
                                      └──看板──→ BI 平台
```

## 2. 核心痛点深度分析

### P0-1：SQL 是重复劳动的最大头

- **现状**：数据分析师的工作中，「写 SQL 取数」占 40-60% 的时间。业务方问一句"上周新用户的次日留存"，分析师需要写一条可能涉及多表 JOIN、子查询、窗口函数的 SQL。这里的矛盾是：**SQL 的逻辑是确定的（取什么数据、怎么聚合、什么口径），但每次都要人手工翻译成代码**。
- **耗时估算**：每周 15-20 小时在写 SQL 上
- **痛苦根源**：
  - 业务问题是自然语言："看下各渠道的新增用户质量"
  - SQL 是精确的代码：`SELECT channel, COUNT(DISTINCT user_id), AVG(留存)... FROM ... WHERE ... GROUP BY ...`
  - 翻译过程纯是脑力消耗，且口径一旦记错就全盘重来
- **Agent 可替代性分析**：
  - 自然语言 → SQL 是 LLM 公认最强的能力之一 ✓
  - 给 Agent 表结构和字段说明 → 生成正确 SQL 的准确率很高 ✓
  - 复杂业务口径（如"活跃用户"的定义在各公司不同）→ 需要人工确认 ✗

结论：Agent 可以完成 80-90% 的日常 SQL 编写工作。

### P0-2：数据清洗是隐形的体力黑洞

- **现状**：取出来的原始数据很少能直接用——空值填充、异常值剔除、格式转换、多表关联后的去重检查。清洗工作比写 SQL 更无聊但也很容易出错。
- **耗时估算**：每个分析任务 20-40% 的时间在清洗上
- **Agent 可替代性分析**：
  - 描述数据格式和清洗规则 → Agent 生成 Python/R 清洗脚本 ✓
  - 自动检测异常值（3-sigma / IQR）并标注 ✓
  - 多数据源格式统一、字段映射 ✓

### P1-1：周报/月报是定期重复的机械劳动

- **现状**：每周/每月固定时间跑同一套 SQL、更新同一套图表、写大同小异的数据解读。完全可自动化但多数公司还是手工做——因为搭建自动化报表的前期投入大。
- **耗时估算**：每周 3-5 小时（周报），每月再加 2-3 小时（月报）
- **Agent 可替代性分析**：
  - Agent 定时触发 SQL → 生成图表 → 写分析文字 → 输出报告 ✓
  - 对比上周/上月数据，自动标注异常变化 ✓

### P1-2：多数据源口径对齐让人崩溃

- **现状**：BI 看板显示 DAU 100w，运营后台显示 95w，数据仓库显示 102w——因为口径不同（是否去重、是否包含测试账号、统计时间窗口不同）。分析师经常需要花大量时间解释「为什么两个数不一样」。
- **耗时估算**：每次口径问题 1-3 小时
- **Agent 可替代性分析**：
  - Agent 读取多个数据源的 SQL 逻辑 → 自动对比口径差异 ✓
  - 生成口径对齐文档 → 减少未来同类问题 ✓

### P2-1：分析结论的表达比分析本身更花时间

- **现状**：分析做完了，结论有了，但把结论写成 PPT/文档——选什么图、写什么文案、怎么排版——可能比分析本身还花时间。
- **Agent 可替代性分析**：
  - 分析数据 + 结论 + 受众 → Agent 生成报告初稿 ✓
  - 自动选择合适的图表类型 ✓

### P2-2：临时取数打断深度分析

- **现状**：正在做一个复杂分析，业务方突然问「帮我查一下昨天XX功能的点击量」。这种打断不仅花时间，还破坏思维的连续性。
- **Agent 可替代性分析**：
  - 业务方直接向 Agent 提问自然语言 → Agent 生成 SQL 并返回结果（自助取数）→ 分析师解放 ✓

### Before vs After

```
Before（一个分析任务 6h）:
  理解需求(0.5h) → 写SQL取数(1.5h) → 清洗数据(1h)
  → 做分析(2h) → 写报告(1h)

After（Agent + 人 3h）:
  口述需求→Agent生成SQL(2min) → 人验证数据(0.5h)
  → Agent清洗(1min) → 人做分析(2h) → Agent生成报告(2min) → 人润色(0.5h)
  节省的全是「翻译」和「格式化」环节
```

## 4. 落地路径

### Phase 1：自然语言 → SQL（3 天）

**做什么**：
1. 整理一份「数据字典」，包含所有常用表的表名、字段名、字段含义、关联关系、常见口径说明
2. 把数据字典 + 10 个历史典型的「业务问题 → SQL」作为示例喂给 Agent
3. 之后日常的取数需求，用自然语言描述，让 Agent 生成 SQL

**用什么工具**：
- Claude Code + 数据库只读 MCP（或先用静态的数据字典做离线验证）
- 也可使用 ChatGPT/Claude + 粘贴数据字典

**最小 Demo**：
```
你是一个数据分析师。以下是我们的数据字典：

【表】
- users: user_id, register_time, channel, status
- orders: order_id, user_id, amount, status, create_time
- user_activity: user_id, login_date, duration_sec

【口径说明】
- 新用户：首次注册时间在统计周期内的用户
- 活跃用户：当天有登录记录的用户
- 付费用户：有已完成订单（status='paid'）的用户
- 次日留存：注册后第2天有登录记录的用户占比

现在，请为以下问题生成 SQL：

"上周各渠道的新增用户数，以及他们的次日留存率和7日内付费转化率"

请同时解释 SQL 的逻辑，方便我确认。
```

**预期收益**：
- SQL 编写时间：1.5h → 10min（确认 + 微调）
- 口径错误率大幅降低

### Phase 2：自动化报表 + 自助取数（1 个月）

**做什么**：
1. 将周报/月报流程 Agent 化：Agent 定时触发 SQL → 生成图表 → 写分析文字
2. 搭建「业务方自助取数 Agent」：业务方在群内/工具中自然语言提问 → Agent 翻译为 SQL → 返回结果

**关键挑战**：
- 数据库只读权限的申请和审批
- 需要建设数据字典的完整性（Agent 只能基于给定的表结构工作）
- 需要设计权限控制（不同业务方可见不同数据范围）

**预期收益**：
- 周报时间：5h → 0.5h
- 临时取数打断减少 70%

### Phase 3：归因分析 + 预测辅助（长期）

**做什么**：
1. 将常见的归因分析方法（漏斗分析、同期群分析、指标拆解）模板化给 Agent
2. 输入异常指标，Agent 自动做多维度下钻分析
3. Agent 辅助做预测：基于历史趋势 + 业务事件，输出预测区间

**预期收益**：
- 异常归因时间：半天 → 1h
- 分析报告更全面（Agent 不会遗漏常见维度）

## 6. 收益预估 & 风险边界

### 量化收益

| 环节 | 纯人工 | Agent + 人 | 节省比例 |
|------|--------|-----------|---------|
| 写 SQL 取数（单次） | 0.5-1.5h | 5-15min | 75-85% |
| 数据清洗 | 0.5-1h | 5-10min | 80% |
| 周报（每周） | 4h | 0.5h | 85% |
| 分析报告撰写 | 1-2h | 15-30min | 70-80% |
| 口径对齐 | 2h | 20min | 80% |
| **每周总计** | **~20h** | **~6h** | **~70%** |

### 不可做的边界

```
✗ Agent 不能替代人的地方：
├── 分析框架设计：面对一个模糊的业务问题，应该从哪入手分析
├── 因果推断：相关性 ≠ 因果，判断什么是真正的原因
├── 业务建议：分析结论如何转化为可落地的业务动作
├── 数据敏感度：发现数据中「不对劲但说不清哪里不对劲」的直觉
├── 利益相关者管理：分析结果可能挑战某些人的利益，怎么说、对谁说
└── 新指标定义：什么指标能真正衡量业务健康度

✗ Agent 使用限制：
├── Agent 生成的 SQL（特别是涉及多表 JOIN 的）必须在测试环境先跑
├── 数据库只读权限可以给，写操作绝不允许 Agent 执行
├── 给外部 Agent 服务的查询中必须脱敏（用户ID、手机号等）
├── 定期审计 Agent 生成的 SQL（检查是否有不必要的全表扫描）
└── 数据字典需要持续维护，过期的表结构描述会让 Agent 出错的 SQL
```

### 常见陷阱

1. **盲目相信 SQL 结果**：Agent 生成的 SQL 语法正确 ≠ 逻辑正确。取出来的数据要先用业务常识验证（数量级对不对？趋势对不对？）。
2. **全表扫描风险**：Agent 可能生成不带分区过滤或者不带索引条件的 SQL，在百万级表上直接崩掉。需要加入「性能检查」环节。
3. **口径漂移**：Agent 基于数据字典生成 SQL，但数据字典可能过时。字段含义变了但数据字典没更新 → Agent 生成的 SQL 口径是错的。
4. **分析同质化**：如果完全依赖 Agent 做分析，所有报告会趋于模板化——缺乏分析师本人对业务的独特洞察。
5. **过度依赖自助查询**：如果业务方直接通过 Agent 取数，没有分析师把关，可能因为口径不一致做出错误决策。
